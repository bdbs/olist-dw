# FIX-008：中文文件名导致 Expand-Archive 解压失败

> 编号：FIX-008
> 日期：2026-09-12
> 严重度：🟡 中（有替代方案，但阻塞交付）
> 状态：✅ 已修复并质检通过

---

## 一、为什么更新

### 1.1 触发

用户执行：

```powershell
Expand-Archive -Path "D:\projects\olist-dw_补丁包_指标层.zip" -DestinationPath . -Force
```

报错：

```
路径中具有非法字符
New-Object / ConstructorInvokedThrowException
```

同时 `dbt test` 仍显示 `PASS=74`，说明**补丁未应用成功**。

### 1.2 根本原因

**Windows PowerShell 5.1 的 `Expand-Archive` 在处理 ZIP 内中文文件名时存在编码缺陷。**

技术细节：

| 层 | 说明 |
|---|---|
| ZIP 规范 | 传统 ZIP 用 **CP437** 编码文件名，中文需 UTF-8 flag（bit 11） |
| .NET 实现 | `Expand-Archive` 底层依赖 `System.IO.Compression.ZipFile`，对 UTF-8 flag 处理不一致 |
| 系统区域 | 中文 Windows 默认 ANSI = **GBK**，与 UTF-8 文件名转换时产生非法字符 |

**这与之前踩的坑同源**：

| 编号 | 坑 | 共同根因 |
|---|---|---|
| 早期 | Python 读中文注释报 GBK 错 | Windows 中文环境默认编码假设 |
| FIX-008 | PowerShell 解压中文文件名报非法字符 | **同上** |

### 1.3 为什么之前没暴露

| 补丁包 | 内部文件名 | 结果 |
|---|---|---|
| FIX006 | `docs/19_update_delivery_spec.md` 等含中文 | 用户**用资源管理器解压**成功，绕过了 |
| 指标层 | 同含中文 | 用户用 `Expand-Archive` → 失败 |

**结论**：不是新问题，是首次在命令行路径上触发。

## 四、为什么这样改（修改逻辑）

### 决策 1：为什么不全用英文文件名

| 方案 | 评价 |
|---|---|
| 全项目改英文文件名 | ❌ 用户已选定中文版，改动面太大 |
| **双包并存 + 英文包用于命令行** | ✅ 选中：中文包给资源管理器，英文包给命令行 |
| 只给中文包 | ❌ 命令行用户持续受阻 |

### 决策 2：为什么推荐资源管理器（方案 A）

| 方案 | 评价 |
|---|---|
| **资源管理器右键解压** | ✅ Windows 资源管理器对 ZIP 中文处理成熟，0 失败率 |
| `Expand-Archive` | ❌ 已验证失败 |
| `tar -xf` | 🟡 Windows 10+ 自带 bsdtar 可解 zip，但版本差异大 |
| Python `zipfile` | ✅ 可靠，但需多敲一行命令 |

**排序理由**：优先选**用户最不需要学习成本**的方案。

### 决策 3：为什么英文包内文档改名 `22_kpi_catalog.md`

保持与英文文件名版项目的命名体系一致。
用户在中文版项目里应用后，可用一条命令重命名：

```powershell
Rename-Item docs\22_kpi_catalog.md "22_kpi_catalog.md"
```

### 决策 4：为什么今后打包优先 ASCII

| 考虑 | 说明 |
|---|---|
| 兼容性 | ASCII 路径在所有 Windows 版本、所有解压工具下 100% 可用 |
| 成本 | 只是包内文件名，不影响用户项目命名体系 |
| 教训 | 已连续踩两次编码坑（Python GBK、PowerShell 非法字符） |

> **通用经验**：
> 在 Windows 中文环境下，**任何跨工具传递的文件路径都应优先用 ASCII**。
> 这是规避编码问题成本最低的手段。
