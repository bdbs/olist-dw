# 数仓建模规范

> 版本：V1.0
> 适用范围：本项目全部数据模型（ODS / DWD / DWS / ADS）
> 性质：开发约束文档，所有模型必须遵守
> 配套：`12_data_model_spec.md`（讲"为什么"）、本文档（讲"必须怎么做"）

---

> 📌 **术语说明**：本文档中的「质检规则」指对数据质量设定的自动校验条件，
> 业内标准术语叫「**断言**」（英文 assert，对应 dbt 的 `test` 功能）。
> 例如「订单ID不能重复」就是一条质检规则。

## 使用说明

本文档是**约束性规范**，不是建议。每条规则标注了执行级别：

| 级别 | 含义 | 违反后果 |
|---|---|---|
| 🔴 **必须** | 强制遵守 | 代码评审不通过 |
| 🟡 **建议** | 强烈推荐 | 需说明理由 |
| ⚪ **可选** | 视情况 | 无 |

## 一、分层规范

### 1.1 四层架构定义

| 层级 | 全称 | 目录 | 物化 | Schema |
|---|---|---|---|---|
| **ODS** | Operational Data Store | `models/staging/` | view | `main_staging` |
| **DWD** | Data Warehouse Detail | `models/marts/core/` | table | `main_core` |
| **DWS** | Data Warehouse Summary | `models/marts/analytics/` | table | `main_analytics` |
| **ADS** | Application Data Store | `models/marts/analytics/` | table | `main_analytics` |

### 1.2 各层职责边界（🔴 必须）

| 层级 | 允许做 | **禁止做** |
|---|---|---|
| **ODS** | 类型转换、字段改名、去空格、大小写统一 | ❌ 业务逻辑<br>❌ 过滤数据（`WHERE`）<br>❌ 聚合（`GROUP BY`）<br>❌ JOIN |
| **DWD** | 星型建模、口径统一、维度派生、多表 JOIN | ❌ 跨主题汇总<br>❌ 面向具体报表 |
| **DWS** | 面向主题的轻度汇总 | ❌ 直接对外服务 |
| **ADS** | 面向具体报表/看板，一表一应用 | — |

**为什么 ODS 禁止 WHERE？**

> ODS 的职责是"忠实记录源数据"。
> 一旦在这一层过滤，下游就永远拿不到被过滤的数据，
> 且**没有任何地方记录"过滤了什么"**——这是静默数据丢失的温床。

### 1.3 依赖方向（🔴 必须）

```
ODS → DWD → DWS → ADS
```

- 只能**上游被下游引用**，严禁反向依赖
- 严禁跨层引用（如 ADS 直接引用 ODS）
- 通过 dbt 的 `ref()` 强制执行，违反会报编译错误

## 二、命名规范

### 2.1 模型命名（🔴 必须）

| 层级 | 前缀 | 格式 | 示例 |
|---|---|---|---|
| ODS | `stg_` | `stg_<业务实体>` | `stg_orders` |
| DWD 维度 | `dim_` | `dim_<主题>` | `dim_customers` |
| DWD 事实 | `fct_` | `fct_<业务过程>` | `fct_orders` |
| DWS | `dws_` | `dws_<主题>_<分析视角>` | `dws_customer_rfm` |
| ADS | `ads_` | `ads_<报表用途>` | `ads_gmv_monthly` |
| 快照 | `snap_` | `snap_<主题>` | `snap_customers` |

**规则**：
- 全部小写
- 单词间用下划线（snake_case）
- 表名用**复数**（如 `customers` 而非 `customer`）
- 禁止拼音、缩写（除非业界通用）

### 2.2 字段命名（🔴 必须）

| 类型 | 规则 | 示例 |
|---|---|---|
| 通用 | 小写 + 下划线 | `customer_id` |
| 主键 | `<实体>_id` | `order_id` |
| 外键 | `<关联实体>_id` | `customer_id` |
| 时间戳 | `_at` 结尾 | `order_purchased_at` |
| 日期 | `_date` 结尾 | `order_date` |
| 布尔 | `is_` 开头 | `is_delivered` |
| 比率 | `_pct` 结尾 | `cancel_rate_pct` |
| 金额 | 带币种或明确单位 | `gmv_delivered` |
| 计数 | `_count` 结尾 | `order_count` |

### 2.3 口径命名规范（🔴 必须 · 本项目重点）

> **同一个指标的不同口径，必须在字段名上区分，不能只靠注释。**

```sql
gmv_all          -- 含取消订单（错误口径，仅供对比）
gmv_delivered    -- ✅ 标准口径（对外统一使用）
gmv_cancelled    -- 取消金额（用于损失分析）
```

**为什么强制？**

如果一个人引用了 `gmv_all` 出报表，
代码评审时**一眼就能看出来**——
这条规则让口径错误在命名阶段就无法隐藏。

### 2.4 禁止的命名（🔴 必须）

```sql
-- ❌ 禁止
CustomerID        -- 驼峰
客户ID            -- 中文
flag / amount1    -- 语义不明
data / info       -- 过于宽泛
temp / test01     -- 临时命名
```

## 三、模型设计规范

### 3.1 粒度声明（🔴 必须）

**每个模型必须在头部注释中声明粒度。**

```sql
-- 粒度：一行 = 一笔订单中的一个商品
```

**选型原则**：

> **尽可能保留最细粒度。**
> 粒度越细，能回答的问题越多。
> 一旦把粒度定粗，细粒度的分析能力**永久丢失**。

| 场景 | 粒度选择 |
|---|---|
| 既要订单汇总又要商品分析 | 订单行（最细） |
| 只关心客户维度 | 客户 |
| 需要时间趋势 | 至少保留到日 |

### 3.2 事实表规范（🔴 必须）

**字段只能有三类**：

| 类型 | 说明 | 本项目 |
|---|---|---|
| **外键** | 指向维度表 | `customer_id`、`product_id` |
| **度量值** | 可聚合的数字 | `price`、`order_amount` |
| **退化维度** | 有业务含义但不必单独建维表 | `order_id`、`order_status` |

**度量值可加性声明**（🟡 建议）：

| 可加性 | 说明 | 示例 |
|---|---|---|
| ✅ 可加 | 可跨任意维度 SUM | 金额、数量 |
| ⚠️ 半可加 | 可跨部分维度 | 库存余额（不能跨时间相加） |
| ❌ 不可加 | 不能相加 | 单价、比率 |

> **禁止把不可加的度量值直接 SUM**——这是常见错误。

### 3.3 维度表规范（🔴 必须）

| 规则 | 说明 |
|---|---|
| 必须有主键 | 且主键唯一、非空 |
| 派生字段下沉 | 口径类计算**必须**放在维度表，禁止在 BI 层写 CASE WHEN |
| 空值兜底 | 字符串维度空值填 `'unknown'`，并加中文说明 |
| 缓慢变化 | 需要保留历史的用 SCD Type 2 |

**派生字段下沉示例**：

```sql
-- ✅ 正确：维度表派生
CASE WHEN customer_state IN ('SP','RJ') THEN TRUE ELSE FALSE END AS is_core_market

-- ❌ 错误：BI 报表里写
-- 每个报表写一遍，标准必然不一致
```

### 3.4 口径下沉规范（🔴 必须 · 治理核心）

**三步法**：

| 步骤 | 动作 | 落地位置 |
|---|---|---|
| ① 标记 | DWD 层统一生成布尔标记位 | `fct_orders.is_delivered` |
| ② 约束 | 下游只准引用标记位，**禁止**自行过滤原始字段 | 代码评审 |
| ③ 固化 | 数据字典写明"对外统一口径" | `schema.yml` |

```sql
-- ✅ 正确：引用标记位
WHERE is_delivered = TRUE

-- ❌ 错误：自行过滤原始字段
WHERE order_status = 'delivered'
```

**同时保留多口径字段**（🟡 建议）：

在 ADS 层同时输出多口径，让差异**可见**而非隐藏。

## 四、SQL 编写规范

### 4.1 文件头注释（🔴 必须）

每个 `.sql` 文件必须包含：

```sql
-- ============================================================
-- 模型：<模型名>（中文说明）
-- 层级：<ODS/DWD/DWS/ADS>
-- 物化：<view/table/incremental/snapshot>
-- 粒度：一行 = <业务含义>
-- ------------------------------------------------------------
-- 【这一层是干什么的？】
-- 【关键设计决策与理由】
-- ============================================================
```

### 4.2 CTE 使用（🟡 建议）

复杂查询必须用 CTE 拆分，禁止嵌套子查询超过 2 层。

```sql
-- ✅ 正确
WITH items AS (...),
     orders AS (...),
     joined AS (...)
SELECT * FROM joined

-- ❌ 错误：嵌套子查询
SELECT * FROM (SELECT * FROM (SELECT ...) ...)
```

### 4.3 JOIN 规范（🔴 必须）

| 规则 | 说明 |
|---|---|
| 明确写明 `INNER` / `LEFT` | 禁止裸写 `JOIN` |
| ON 条件必须完整 | 多字段关联要写全 |
| 关联字段类型一致 | 类型不一致会导致隐式转换、索引失效 |
| **必须评估丢失风险** | 用 INNER JOIN 时，要清楚丢了多少、是否有意 |

⚠️ **JOIN 丢失检查**：

```sql
-- 上线前必须跑：确认 INNER JOIN 丢了多少
SELECT COUNT(*) FROM 左表 l
LEFT JOIN 右表 r ON l.id = r.id
WHERE r.id IS NULL;
```

### 4.4 空值处理（🔴 必须）

```sql
-- 算术运算必须防 NULL 传染
COALESCE(price, 0) + COALESCE(freight_value, 0) AS order_amount

-- ❌ 错误：100 + NULL = NULL
price + freight_value AS order_amount
```

### 4.5 禁止事项（🔴 必须）

```sql
SELECT *                      -- ❌ 生产环境禁止（本项目 ODS 层除外）
WHERE 1=1                     -- ❌ 无意义
-- 魔法数字                    -- ❌ 禁止，用注释说明或定义为变量
WHERE amount > 100000         -- ❌ 应注释说明为何是 100000
```

## 五、质量规则规范

### 5.1 质检规则覆盖要求（🔴 必须）

| 层级 | 必配质检规则 |
|---|---|
| **ODS** | 主键 unique + not_null |
| **DWD 维度** | 主键 unique + not_null |
| **DWD 事实** | 主键 unique、外键 relationships、度量值值域 |
| **DWS/ADS** | 主键 unique、关键指标非空 |

### 5.2 五类质量规则（对应 DAMA 六维度）

| 维度 | 质检规则类型 | 示例 |
|---|---|---|
| **唯一性** | `unique` | 主键不重复 |
| **完整性** | `not_null` | 关键字段非空 |
| **有效性** | `accepted_values` | 状态在枚举范围内 |
| **一致性** | `relationships` | 外键存在于维度表 |
| **准确性** | `assert_value_range` | 金额在合理区间 |

### 5.3 告警级别规范（🟡 建议）

| 级别 | 使用场景 | 本项目示例 |
|---|---|---|
| `error`（默认） | 违反即阻断发布 | 主键重复、外键失效 |
| `warn` | 允许存在但必须可见 | **775 单无明细订单** |
| `info` | 仅提示 | — |

> **`severity: warn` 的治理含义**：
> "我知道它存在，并且我在监控它。"
> 适用于业务上无法根治、但必须可见的问题。

### 5.4 质检规则不通过处理流程（🔴 必须）

```
1. 定位   → 回溯到 ODS 层原始数据，确认是采集/录入/逻辑哪类问题
2. 量化   → 统计影响行数、占比
3. 判断   → 采集丢失 / 业务确实如此 / 模型逻辑错误
4. 处理   → 过滤 / 置空 / 归入异常表 / 补兜底维度
5. 防复发 → 补充质检规则，并记录进《数据质量问题台账》
```

**每一步都要留下记录。**

## 六、元数据规范

### 6.1 schema.yml 编写要求（🔴 必须）

| 要求 | 说明 |
|---|---|
| 每个模型必须有 `description` | 说明用途、**粒度**、来源 |
| 每个字段必须有 `description` | 说明业务含义、单位、**口径** |
| 关键字段必须有 `tests` | 见 5.1 |

### 6.2 description 写法（🔴 必须）

```yaml
# ✅ 正确：单行，语义完整
- name: gmv_delivered
  description: "标准 GMV 口径（仅已送达订单）。对外报表统一使用此字段。"

# ❌ 错误：折叠块，缩进敏感易报错
- name: gmv_delivered
  description: >
    标准 GMV 口径...
```

> **强制单行**：YAML 的 `>` 折叠块对缩进极敏感，
> 中文内容极易触发 `did not find expected key` 错误。

### 6.3 粒度必须在描述中声明（🔴 必须）

```yaml
models:
  - name: fct_orders
    description: "订单明细事实表。粒度：一行 = 一笔订单中的一个商品。"
```

## 七、物化策略规范

| 场景 | 物化方式 | 理由 |
|---|---|---|
| ODS 贴源层 | `view` | 不占存储，永远与源一致 |
| 被高频引用的中间层 | `table` | 避免重复计算 |
| 直接服务 BI | `table` | 要求响应快 |
| 数据量大且只增不改 | `incremental` + `append` | 提升刷新效率 |
| 数据会被修改 | `incremental` + `merge` | 保证更新生效 |
| 需保留历史版本 | `snapshot`（SCD2） | 支持时点回溯 |

### 增量模型必检项（🔴 必须）

| 检查项 | 说明 |
|---|---|
| `unique_key` 是否设置 | 用于判断重复 |
| 迟到数据处理 | 是否加回溯窗口 |
| 历史修改处理 | 是否需 merge 或定期全量重建 |

## 八、代码评审 Checklist

提交前逐项自检：

### 命名
- [ ] 模型前缀符合层级规范（`stg_`/`dim_`/`fct_`/`dws_`/`ads_`）
- [ ] 字段小写 + 下划线
- [ ] 布尔用 `is_` 开头，比率用 `_pct` 结尾
- [ ] 多口径指标在字段名上已区分

### 结构
- [ ] 文件头注释完整（含粒度声明）
- [ ] 分层职责未被违反（ODS 无 WHERE / 无 JOIN）
- [ ] 依赖方向正确，无跨层引用
- [ ] 使用了 `ref()` 而非硬编码表名

### 逻辑
- [ ] 算术运算有 `COALESCE` 防空值
- [ ] JOIN 类型明确，且评估过丢失影响
- [ ] 口径引用的是 DWD 标记位，未自行过滤原始字段
- [ ] 度量值可加性正确（未对不可加字段 SUM）

### 质量
- [ ] 主键有 `unique` + `not_null`
- [ ] 外键有 `relationships`
- [ ] 枚举字段有 `accepted_values`
- [ ] 数值字段有值域质检规则
- [ ] 已知问题已设 `severity: warn`

### 元数据
- [ ] 模型和字段 `description` 齐全
- [ ] `description` 用单行字符串
- [ ] 粒度已在描述中声明
- [ ] 口径已在描述中写明

## 九、规范执行与例外

### 例外处理

任何规范例外必须：
1. 在代码注释中写明**理由**
2. 在 PR 描述中说明
3. 记录进《数据质量问题台账》或技术债清单

### 本项目已知例外

| 例外 | 位置 | 理由 |
|---|---|---|
| ODS 层使用 `SELECT *` | `stg_*.sql` | 贴源层职责就是原样搬运，显式列出反而易漏字段 |
| 卖家未单独建维表 | `fct_orders.seller_id` | 项目范围所限，卖家维度非分析重点 |
| 775 单无明细订单未修复 | `fct_orders` | 业务客观存在，采用监控而非修复策略 |
