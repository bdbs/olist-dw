# 代码业务解读手册：从业务角度理解 SQL

> 版本：V1.0
> 日期：2026-09-12
> 定位：**治理岗核心能力**——把技术决策讲成业务故事
> 配套：`12_data_model_spec`（讲结构）、`20_术语对照表`（讲名词）

## 一、为什么你需要这个视角


|---|---|---|
| **开发岗** | 能不能实现 | "这个需求 SQL 怎么写？" |
| **治理岗** | **该不该这么做** | "**为什么**这么设计？换个方式行不行？" |

**治理岗的本质是"做决策并解释决策"**，不是"写代码"。

### 1.2 一个真实对比

同一件事，两种讲法：

|---|---|---|
| ❌ 技术讲法 | "我用 `ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY review_created_at DESC)` 取了最新一条评价" | 点点头："哦，会写窗口函数" |
| ✅ **业务讲法** | "我发现一笔订单可能有多条评价，如果不过滤，JOIN 之后金额会**虚高 12.5%**——这个错误**不报错**，报表看起来完全正常。所以我定了规则：每笔订单只取最新一条作为有效评价，其余保留但打标记" | 追问："你怎么发现的？""为什么保留而不是删除？" → **你有话讲** |

**差距在哪**：第二种讲法包含了**风险、决策、取舍**——这才是治理岗的价值。

## 二、核心认知：代码是业务规则的固化

> ⭐ **这是全篇最重要的一句话**：
> **每一行代码背后，都是一个业务决策。**

看代码时不要问"这行 SQL 做什么"，
要问"**这行 SQL 替谁做了什么决定**"。

### 例子

```sql
CASE WHEN order_status = 'delivered' THEN TRUE ELSE FALSE END AS is_delivered
```

| 视角 | 理解 |
|---|---|
| 技术视角 | 生成一个布尔字段 |
| **业务视角** | **定义了"什么才算真实收入"**——这是财务口径的固化 |

**一旦这么看，代码就不再是语法，而是"写进数据库的业务制度"。**

这也解释了为什么治理岗要懂代码：**不懂代码，你连公司里到底有哪些"隐性制度"都不知道。**

## 三、四问法框架（可复用）

看到任何一段代码，问自己这四个问题：

```
问 1：这段在解决什么业务问题？
问 2：不这样做，业务上会出什么事？（能量化最好）
问 3：它替谁做了什么决定？
问 4：业务规则变了，要改哪里？
```

**为什么是这四问**：

| 问题 | 对应能力 |
|---|---|
| 问 1 | 理解业务 |
| 问 2 | **风险意识**（治理岗核心） |
| 问 3 | 决策意识 |
| 问 4 | 影响分析 |

> 每个模型讲 1 分钟，逻辑清晰且有深度。

### 案例 1：GMV 口径标记位 ★ 最能体现治理价值

#### 代码

```sql
-- models/marts/core/fct_orders.sql
CASE WHEN o.order_status = 'delivered' THEN TRUE ELSE FALSE END AS is_delivered,
CASE WHEN o.order_status = 'canceled'  THEN TRUE ELSE FALSE END AS is_canceled
```

#### 四问法解读

**问 1：解决什么业务问题？**

> "公司的 GMV 到底算多少钱？"

一个订单从创建到完成有多个状态：已创建、已付款、已发货、**已送达**、**已取消**。
只有"已送达"的钱，才是真正进口袋的收入。

**问 2：不做会怎样？（实测数据）**

| 口径 | 金额 |
|---|---|
| 含全部订单 | **15,843,553 BRL** |
| 仅已送达 | **15,419,774 BRL** |
| **差异** | **423,779 BRL（2.67%）** |

**危害不在于差 2.67%，而在于**：
- 财务部用一个数，运营部用另一个数
- 开会时谁也说服不了谁
- **没人知道谁是对的**

**问 3：替谁做了什么决定？**

> 替**全公司**决定了："GMV 的标准定义 = 已送达订单金额"。

这个决定**写在 DWD 层**（数仓中间层），而不是：
- ❌ 写在 BI 报表里（每张报表可能写得不一样）
- ❌ 留在人脑里（人会离职、会记错）

**问 4：业务规则变了改哪里？**

如果将来"已发货但未送达"也算收入：
**只改这一处**，所有下游报表自动同步。

### 案例 2：INNER JOIN 与 775 单静默丢失 ★ 最有深度

#### 代码

```sql
FROM {{ ref('stg_order_items') }} i
INNER JOIN {{ ref('stg_orders') }} o
    ON i.order_id = o.order_id
```

#### 四问法解读

**问 1：解决什么业务问题？**

把"订单明细"和"订单主表"拼起来，才能知道每个商品属于哪笔订单、哪个客户。

**问 2：不做 / 换做法会怎样？**

**这是全项目最有价值的一个发现**：

```
源订单总数        99,441
事实表去重订单数   98,666
静默丢失             775（0.78%）
```

**为什么丢**：这 775 笔订单在明细表里**没有对应记录**（下了单但没商品，可能是数据同步问题）。
`INNER JOIN` 只保留两边都有的，所以它们**无声无息地消失了**。

**危害排序**：

| 问题类型 | 危险程度 | 原因 |
|---|---|---|
| 算错 | 🟡 中等 | 两个数字一对比就发现 |
| **静默丢失** | 🔴 **最高** | **你根本不知道少了** |

> "算错不可怕，可怕的是丢了你不知道。"

**问 3：替谁做了什么决定？**

决定：**事实表粒度保持纯洁**（一行 = 一个商品行）。

那 775 单**为什么不补回来**？这是我做过最难的取舍：

| 方案 | 做法 | 后果 |
|---|---|---|
| A | 改 `LEFT JOIN` 把订单补回来 | ❌ 会产生 775 行"没有商品的订单明细"，污染所有金额聚合 |
| B | **保持 INNER JOIN** | ✅ 粒度纯洁，另在 ADS 层建订单总数指标 |

**选 B 的理由**：
事实表一旦混入不完整行，所有下游 `SUM`、`AVG` 都会受影响，
**修一个问题的代价是制造十个新问题**。

**问 4：业务规则变了改哪里？**

如果业务要求"订单量必须包含无明细订单"：
在 ADS 层单独建指标（KPI004 已经这么做了，取源表口径），
**不动事实表**。

### 案例 3：未知品类兜底

#### 代码

```sql
-- models/marts/core/dim_products.sql
COALESCE(p.product_category_name, 'unknown') AS product_category_name
```

#### 四问法解读

**问 1：解决什么业务问题？**

真实数据有 **610 条商品没有品类**。

**问 2：不兜底会怎样？**

维度表 JOIN 时，`NULL` 会导致这些商品的销售记录**整行丢失**：

```
有兜底：610 条商品归入"未知品类"，销售额仍在总数内
无兜底：610 条商品的销售额凭空消失，且无人察觉
```

**又是"静默丢失"**——和 775 单同一类问题。

**问 3：替谁做了什么决定？**

替**分析师**决定：看到"未知品类"时知道这是数据缺失，不是真空品类。

**关键设计**：用 `'unknown'` 而不用 `NULL`，
因为 `NULL` 在 `GROUP BY` 中会被单独分组且容易在报表中显示为空白，
业务方会以为是系统 bug。

**问 4：业务规则变了改哪里？**

如果业务要求把这 610 条按商品名关键词自动归类：
只改这一行 `COALESCE`。

### 案例 4：一单多评与 fan-out 防护 ★ 技术含量最高

#### 代码

```sql
-- models/marts/core/fct_reviews.sql
ROW_NUMBER() OVER (
    PARTITION BY r.order_id
    ORDER BY r.review_created_at DESC NULLS LAST
) AS rn,

COUNT(*) OVER (PARTITION BY r.order_id) AS order_review_count
```

#### 四问法解读

**问 1：解决什么业务问题？**

一笔订单可能被评价多次（客户补充评价、系统重复提交）。
业务上应该"一笔订单只算一次满意度"。

**问 2：不做会怎样？（实测）**

```
❌ 错误写法（直接 JOIN 评价表）：3,803,285.63
✅ 正确金额（事实表原值）      ：3,381,281.72
⚠️  金额虚高 12.5%
```

这叫 **fan-out（扇出）**——JOIN 后行数膨胀，导致 `SUM` 翻倍。

**生活比喻**：
> 复印文件时把同一页多印了几份，
> 装订时总页数就虚高了。
> 而且**每一页看起来都正常**，你不会发现多印了。

**问 3：替谁做了什么决定？**

决定：
- **保留**全部评价记录（不删除，保留可追溯性）
- 但**标记**哪条是"有效评价"（`is_latest_review`）
- 下游分析时用它过滤

**为什么不直接删？**

| 方案 | 后果 |
|---|---|
| 直接删旧评价 | ❌ 丢失客户修改评价的行为轨迹，无法分析"客户为什么改评价" |
| **保留 + 标记** | ✅ 默认取最新，需要时仍能查历史 |

**问 4：业务规则变了改哪里？**

如果业务改为"取平均分"而非"取最新"：
改 `is_latest_review` 的逻辑，或新增 `avg_score` 字段。
**下游报表不用动**——因为它们只认标记位。

### 案例 5：RFM 客户分层 ★ 业务含义最丰富

#### 代码

```sql
-- models/marts/analytics/dws_customer_rfm.sql
NTILE(4) OVER (ORDER BY last_order_date) AS r_score,
NTILE(4) OVER (ORDER BY frequency)       AS f_score,
NTILE(4) OVER (ORDER BY monetary)        AS m_score,

CASE
    WHEN r_score >= 3 AND f_score >= 3 AND m_score >= 3
        THEN '高价值客户'
    WHEN r_score <= 1 AND m_score >= 3
        THEN '重要挽留客户'
    ...
END AS rfm_segment
```

#### 四问法解读

**问 1：解决什么业务问题？**

> "有限的营销预算，该花在哪些客户身上？"

**问 2：不做会怎样？**

营销资源平均分配 → 高价值客户被忽视、已流失客户被反复骚扰。

**问 3：替谁做了什么决定？**

这段代码的业务含义，用大白话说：

| 维度 | 英文 | 业务问题 |
|---|---|---|
| **R** | Recency | 最近一次购买**多久以前**？ |
| **F** | Frequency | 一共买了**多少次**？ |
| **M** | Monetary | 一共花了**多少钱**？ |

**`NTILE(4)` 的业务含义**：
把客户按某个维度**均分成 4 档**（各占 25%）。

> 为什么用相对排名而不是绝对阈值？
> 因为"花了 1000 块算多还是少"取决于整体水平。
> **NTILE 保证每档都有 25% 的客户**，分层永远均衡。

**各分层的业务动作**：

| 分层 | 业务含义 | 该做什么 |
|---|---|---|
| **高价值客户** | 三项都高 | 重点维护，VIP 服务 |
| **重要挽留客户** | **花得多但很久没来** | 🔴 **最优先召回**——这是最危险的信号 |
| **新客/低价值** | 最近来了但花得少 | 培养，提升首次客单价 |
| **流失客户** | 又久没来、买得又少 | 低成本唤醒，不投大预算 |
| **一般客户** | 其余 | 常规运营 |

> 💡 **"重要挽留客户"为什么最优先**？
> 这类客户**证明过自己的消费能力**（M 高），
> 只是最近没来（R 低）。
> 相比拉新客，召回他们的**成本更低、成功率更高**。

**问 4：业务规则变了改哪里？**

如果运营要求分成 5 档而非 4 档：
把 `NTILE(4)` 改成 `NTILE(5)`，并调整 `CASE WHEN` 的阈值。

### 案例 6：地理维度聚合（100万 → 1.9万）

#### 代码

```sql
-- models/marts/core/dim_geography.sql
SELECT
    geolocation_zip_code_prefix,
    AVG(geolocation_lat) AS avg_lat,
    AVG(geolocation_lng) AS avg_lng,
    COUNT(*) AS measurement_count
FROM {{ ref('stg_geolocation') }}
GROUP BY geolocation_zip_code_prefix
```

#### 四问法解读

**问 1：解决什么业务问题？**

`geolocation` 源表有 **100 万行**，但同一个邮编重复几百次
（不同测量点测出的经纬度略有差异）。

**问 2：不聚合会怎样？**

直接用 100 万行去 JOIN：

```
一笔订单 × 一个邮编的 500 条测量记录 = 500 行
```

**又一个 fan-out**——销售额直接翻 500 倍。

**问 3：替谁做了什么决定？**

决定：**一个邮编 = 一个位置**，用所有测量点的**平均值**作为该区域中心。

这叫**区域质心**——地理信息系统的标准做法。

**为什么保留 `measurement_count`？**

| 理由 | 说明 |
|---|---|
| 可追溯 | 能查到这个邮编有多少个原始测量点 |
| 质量信号 | 测量点越少，平均值越不可靠 |
| 不丢信息 | 聚合不可逆，保留计数能部分还原 |

**问 4：业务规则变了改哪里？**

如果业务要求用"中位数"而非"平均值"（抗极端值）：
改 `AVG` 为 `MEDIAN`。

## 五、常见代码模式 → 业务含义速查

看代码时对照这张表：

| 代码写法 | 技术含义 | **业务含义** |
|---|---|---|
| `CASE WHEN ... THEN ... END` | 条件分支 | **业务规则的固化**（如：什么算有效订单） |
| `COALESCE(a, b)` | 空值替换 | **缺失数据的兜底策略** |
| `INNER JOIN` | 内连接 | 只保留两边都有的 → **可能静默丢数据** |
| `LEFT JOIN` | 左连接 | 保留主表全部 → **可能产生空行污染** |
| `ROW_NUMBER() OVER` | 行编号 | **"取最新/最大一条"的决策** |
| `NTILE(n)` | 分档 | **相对排名分层**（保证每档比例均衡） |
| `GROUP BY` | 分组聚合 | **改变粒度**（从明细到汇总） |
| `COUNT(DISTINCT x)` | 去重计数 | 防止重复计算客户/订单 |
| `SUM(CASE WHEN ...)` | 条件求和 | **按口径拆分统计** |
| `WHERE is_latest_review` | 过滤标记位 | **引用既定口径，不自行判断** |
| `severity: warn` | 告警级别 | "允许存在，但必须可见" |
| `ref('模型名')` | 依赖引用 | **血缘的来源**（自动生成依赖关系） |

## 六、技术决策 → 业务故事的转换公式


```
① 业务问题   →  "业务上要解决什么？"
② 风险量化   →  "不处理会出什么事？"（必须有数字）
③ 我的决策   →  "我怎么做的，为什么"
④ 取舍说明   →  "我放弃了什么，为什么值得"
⑤ 防复发     →  "怎么保证问题不再悄悄发生"
```

### 完整示范（775 单案例）

| 步骤 | 内容 |
|---|---|
| ① 业务问题 | 订单量与事实表统计对不上 |
| ② 风险量化 | 99,441 vs 98,666，**静默丢失 775 单（0.78%）** |
| ③ 我的决策 | 保持 INNER JOIN，粒度纯洁优先 |
| ④ 取舍说明 | 放弃改 LEFT JOIN，因为会污染所有金额聚合 |
| ⑤ 防复发 | ADS 层另建订单总数指标 + warn 级规则持续监控 |

## 八、本次文档说明

### 8.1 为什么新增

| 项 | 内容 |
|---|---|
| **触发** | 用户反馈："很多代码级别的逻辑及原理我不理解，我需要从业务角度理解代码，并能解释为什么这样做" |
| **根因** | 此前的交付偏工程实践（怎么做），缺少业务视角（为什么这么做） |
| **含义** | 治理岗的核心能力是**解释决策**，不是实现功能 |

### 8.2 为什么用"四问法"

| 备选 | 评价 |
|---|---|
| 逐行注释代码 | ❌ 仍停留在技术视角 |
| 只讲业务不讲代码 | ❌ 无法定位到具体实现 |
| **四问法（问题-风险-决策-变更）** | ✅ 选中：每个问题都逼出业务含义 |

**设计依据**：
问 2「不做会怎样」是治理岗区别于开发岗的关键——
**开发关注"怎么做对"，治理关注"不做会错成什么样"**。

### 8.3 配套关系

| 文档 | 回答什么 |
|---|---|
| `12_data_model_spec` | 结构：有哪些表、什么关系 |
| `20_术语对照表` | 名词：断言是什么、粒度是什么 |
| **`23_代码业务解读`（本文档）** | **为什么：这段代码背后的业务决策** |

三份文档构成完整认知链：**是什么 → 叫什么 → 为什么**。
