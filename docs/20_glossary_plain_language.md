## 一、数据质量类

### 质检规则（业内叫「断言」/ assert）

| 项 | 内容 |
|---|---|
| **大白话** | 给数据定的**自动检查条件**，不满足就报错 |
| **生活比喻** | 工厂出厂前的**质检关卡**——每个产品都要过检具，不合格就拦下 |
| **英文** | assert（断言）、test（测试） |
| **技术实现** | dbt 的 `test` 功能 |

**具体长什么样**：

```
规则1：订单ID不能重复        → 重复就报错
规则2：客户ID不能为空        → 有空值就报错
规则3：订单状态只能是指定的几种 → 出现新状态就报错
规则4：金额不能是负数        → 有负数就报错
```

**为什么要叫"断言"**：

> 「断言」= 断定 + 声称。
> 我**断言**"订单ID应该不重复"——
> 如果实际有重复，说明我的断言错了，或者数据脏了。
> 这是从编程借来的词（`assert` 语句）。


```
✅ 建立 74 项数据质检规则（唯一性/完整性/有效性/一致性/准确性），通过率 100%
✅ 设计 74 项自动化数据质量校验规则，覆盖唯一性、完整性、有效性、一致性、准确性五个维度
```


> "我给数据定了 74 条自动检查规则，业内叫断言。
> 比如订单ID不能重复、金额不能为负、状态只能在指定范围内。
> 每次数据更新都会自动跑一遍，不通过就阻断发布。"

---

### 五个质量维度（DAMA 标准）

| 维度 | 大白话 | 生活比喻 | 本项目例子 |
|---|---|---|---|
| **唯一性** | 不能重复 | 身份证号不能有两个人用 | 订单ID不重复 |
| **完整性** | 不能为空 | 快递单不能没写收件人 | 客户ID非空 |
| **有效性** | 要在允许范围内 | 性别只能填男/女 | 订单状态8种之一 |
| **一致性** | 关联要对得上 | 订单里的客户必须在客户表里 | 外键存在 |
| **准确性** | 数值要合理 | 年龄不能填 200 | 金额非负 |

> 这五个维度是 **DAMA 数据管理知识体系**的标准划分，
> 也是 DCMM 数据质量能力域的评估依据。

---

### 告警级别（severity）

| 级别 | 大白话 | 什么时候用 |
|---|---|---|
| `error` | 红灯，**阻断发布** | 主键重复、外键失效 |
| `warn` | 黄灯，**放行但告警** | 已知问题，持续监控 |
| `info` | 蓝灯，仅提示 | — |

**`warn` 的治理含义**（本项目重点）：

> "我知道它存在，并且我在监控它。"
>
> 适用于业务上无法根治、但必须可见的问题。
> 例如 775 单无明细订单——删不掉，但必须让所有人知道。

## 二、建模类

### 粒度（Granularity）

| 项 | 内容 |
|---|---|
| **大白话** | 表里**一行数据代表什么** |
| **生活比喻** | 照片的像素——像素越细，能看清的细节越多 |

**例子**：

```
订单表：一行 = 一笔订单
明细表：一行 = 一笔订单中的一个商品   ← 更细
```

**为什么重要**：

> **尽可能保留最细粒度。**
> 粒度一旦定粗，细粒度的分析能力**永久丢失**。

---

### 维度表 / 事实表

| 类型 | 大白话 | 生活比喻 | 本项目 |
|---|---|---|---|
| **维度表** | 描述"谁、什么、哪里" | 名词 | `dim_customers` |
| **事实表** | 记录"发生了什么、多少" | 动词 + 数字 | `fct_orders` |

**记忆口诀**：

> 维度表回答 **5W**（Who / What / Where / When / Why）
> 事实表回答 **How many**（多少）

---

### 星型模型（Star Schema）

**大白话**：一张事实表在中间，周围围着一圈维度表，连线像星星。

```
        dim_customers
              |
dim_products — fct_orders — dim_sellers
              |
        dim_geography
```

**为什么用星型**：
- 简单，业务方容易理解
- JOIN 少，查询快
- 是维度建模最主流的模型

---

### 一致性维度（Conformed Dimension）

**大白话**：同一个含义的维度，在不同表里**口径必须一致**。

**本项目**：`dim_sellers.region` 和 `dim_customers.region` 划分标准完全一样。

**为什么要**：

> 如果不一致，跨主题分析的结果就是错的。
> 比如"本州卖家卖给本州客户的占比"——
> 两边 region 划分不同，算出来毫无意义。

---

### SCD（缓慢变化维）

| 类型 | 大白话 | 例子 |
|---|---|---|
| **Type 1** | 直接覆盖，不留历史 | 客户搬家，城市直接改成新的 |
| **Type 2** | 保留历史版本 | 加「生效时间/失效时间」两列 |

**为什么要 Type 2**：

```
1月：客户住圣保罗
2月：搬到里约

如果直接覆盖 → 1月的订单"看起来"也发生在里约 → 分析失真
```

## 三、dbt 相关

### ref()

**大白话**：告诉 dbt"我这个模型要用到那个模型"。

**为什么不直接写表名**：

| 直接写表名 | 用 `ref()` |
|---|---|
| 环境切换（dev→prod）就跑不了 | 自动切换 |
| 不知道该先跑哪个模型 | **自动解析依赖顺序** |
| 血缘图要手工画 | **自动生成** |

> **你看到的血缘图不是画出来的，是 `ref()` 推出来的。**

---

### 物化（Materialization）

**大白话**：这个模型最终**以什么形式存在**数据库里。

| 策略 | 大白话 | 本项目 |
|---|---|---|
| `view` | 不存数据，每次现算 | ODS 层 |
| `table` | 真的建一张表 | DWD/DWS/ADS |
| `incremental` | 只加新数据 | 大事实表 |
| `snapshot` | 保留历史版本 | SCD Type 2 |

---

### 血缘（Lineage）

**大白话**：数据**从哪来、经过哪些加工、到哪去**的完整链路。

**生活比喻**：食品的**溯源标签**——能查到原料产地、加工环节、运输路径。

**为什么重要（治理岗核心）**：

| 场景 | 血缘的用处 |
|---|---|
| 某个指标错了 | **倒查**是哪一层加工出问题 |
| 要改某个字段 | **正查**会影响哪些下游报表 |
| 新同事接手 | 一张图看懂整个数仓 |

## 四、数据架构类

### ODS / DWD / DWS / ADS

| 层级 | 大白话 | 一句话职责 |
|---|---|---|
| **ODS** | 原始数据照搬 | "原样搬进来，不加工" |
| **DWD** | 清洗整理后的明细 | "整理成规范的结构" |
| **DWS** | 按主题轻度汇总 | "按分析视角预聚合" |
| **ADS** | 面向具体报表 | "一张表一个看板" |

**记忆办法**：

```
原始 → 整理 → 汇总 → 应用
搬砖 → 砌墙 → 装修 → 交付
```

---

### ELT vs ETL

| 范式 | 流程 | 转换在哪做 |
|---|---|---|
| **ETL**（老） | 抽取 → **转换** → 加载 | 专门的转换服务器 |
| **ELT**（新） | 抽取 → 加载 → **转换** | **在数仓里用 SQL 做** |

**本项目是 ELT**：CSV 先装进 DuckDB，dbt 再用 SQL 转换。

**dbt 只做 T**（转换），不管抽取和调度。

## 五、本项目专属概念

### 静默数据丢失

**大白话**：数据少了，但**没有任何报错、没有任何日志**。

**本项目实例**：775 笔订单在明细表没有对应记录，
INNER JOIN 会**无声无息**地把它们丢掉。

**为什么危险**：

> 算错不可怕——两个数字一对比就发现了。
> **丢了才可怕**——你根本不知道少了。

---

### fan-out（扇出）

**大白话**：JOIN 之后行数变多了，导致**金额 SUM 翻倍**。

**生活比喻**：复印文件时把同一页多印了几份，装订时总页数就虚高了。

**本项目实例**：

```
一笔订单 3 个商品 × 2 条评价 = JOIN 后 6 行
SUM(金额) 直接翻倍
```

**实测**：直接 JOIN 导致金额虚高 **12.5%**。

**规避方法**：**先各自聚合到同一粒度，再 JOIN**。

---

### 口径

**大白话**：**一个指标到底怎么算**。

**本项目核心案例**：

| 口径 | 金额 |
|---|---|
| 含全部订单 | 15,843,553 BRL |
| **仅已送达（标准）** | **15,419,774 BRL** |
| 差异 | 423,779 BRL（2.67%） |

> "口径不统一"是数据治理最经典的问题：
> 同一个"GMV"，财务部算出来 A，运营部算出来 B，
> 开会时谁也说服不了谁。

---

### 口径下沉

**大白话**：把"指标怎么算"的约定，**写进数仓代码里**，而不是留在 BI 层或人脑里。

**三步法**：

| 步骤 | 动作 |
|---|---|
| ① 标记 | DWD 层生成布尔标记位（如 `is_delivered`） |
| ② 约束 | 下游只准引用标记位，禁止自行过滤原始字段 |
| ③ 固化 | 数据字典写明"对外统一口径" |
