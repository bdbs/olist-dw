## Q1：无明细订单（孤儿订单）★ 核心案例

### 发现

数据探查时发现：订单表 99,441 单，但订单明细表只覆盖 98,666 单。

```sql
SELECT COUNT(*) AS 无明细订单数
FROM raw_orders o
LEFT JOIN raw_order_items i ON o.order_id = i.order_id
WHERE i.order_id IS NULL;
-- 结果：775
```

### 现象

**775 笔订单在订单表存在、但在明细表没有对应记录。**

这类订单的典型成因：
- 下单后未完成支付，未生成订单行
- 系统异常导致写入中断
- 订单被合并或迁移时遗漏

### 危害（为什么这是最危险的问题）

**INNER JOIN 会让这 775 单静默消失，且没有任何报错。**

```sql
-- 危险写法：775 单无声消失
FROM order_items i
INNER JOIN orders o ON i.order_id = o.order_id
```

从 `order_items` 出发做 INNER JOIN，所有 112,650 行明细都能匹配到订单，
**表面上一行不丢**。但那 775 个"只有订单没有商品"的订单，
**永远不会出现在事实表里**。

后果：
- 从 `fct_orders` 统计订单数 → 得到 98,666，**少算 775 单（0.78%）**
- 没有任何报错、没有日志、没有告警
- 业务看到"昨日订单量下降"时，无从判断是真的下降还是数据丢失

### 处理方案

采用**三层防御**，而非简单改 JOIN：

**① 保留 INNER JOIN，但显式记录丢弃量**

事实表粒度是"订单行"，本来就只应包含有明细的订单。
强行改成 LEFT JOIN 会让事实表出现 `product_id IS NULL` 的脏行，
污染所有下游聚合。**粒度纯洁性优先。**

**② 在 ADS 层建立订单总数监控**

需要"订单总数"时，从 `stg_orders` 直接聚合，而非从事实表反推：

```sql
-- ads 层：订单量指标的两种口径
COUNT(DISTINCT order_id)                    -- 事实表口径：98,666
-- vs
(SELECT COUNT(*) FROM stg_orders)           -- 订单表口径：99,441
```

**③ 补质检规则持续监控**

```yaml
# 在 stg_orders 上加质检规则，监控孤儿订单数量
- name: order_id
  tests:
    - relationships:
        to: ref('stg_order_items')
        field: order_id
        severity: warn    # 设为 warn：允许存在，但必须可见
```

> **`severity: warn` 的设计意图**：
> 这类问题无法"修复"（业务上确实存在无明细订单），
> 但必须**可见**。设为 warn 而非 error，
> 是"我知道它存在，并且我在监控它"的治理态度。

### 方法论沉淀

| 原则 | 说明 |
|---|---|
| **丢失比错误更可怕** | 错误会报错，丢失不会。数据工程中最危险的是静默数据丢失 |
| **可见即可控** | 无法根治的问题，至少要让它出现在监控里 |
| **粒度纯洁性** | 事实表的粒度不能被"方便"破坏，宁可另建指标也不要污染 |
| **先量化再决策** | 0.78% 的丢失率，可以接受但必须知情；如果是 7.8% 则必须根治 |

## Q2：商品品类缺失

### 发现

```sql
SELECT COUNT(*) FROM raw_products
WHERE product_category_name IS NULL;
-- 结果：610
```

### 影响

- 这 610 个商品无法参与品类分析
- 若维度表直接 INNER JOIN，这 610 个商品的销售记录会被**连带丢弃**
- 若用 LEFT JOIN 但不处理 NULL，品类维度会出现空值分组

### 处理

在 `dim_products` 中做**未知兜底**：

```sql
COALESCE(product_category_name, 'unknown')  AS product_category,
CASE WHEN product_category_name IS NULL
     THEN '未知品类' ELSE <中文映射> END      AS product_category_cn
```

**为什么用 COALESCE 兜底而不是过滤掉？**

过滤会丢失这 610 个商品的销售金额，导致 GMV 少算。
兜底则保留金额，同时在"未知品类"分组下**显式暴露**——
分析师一眼能看到"未知品类"占比多少，判断是否需要治理。

> **治理原则**：宁可让问题**可见地存在**，也不要让它**隐形地消失**。

### 质检规则

```yaml
- name: product_category_name
  tests:
    - not_null:
        severity: warn    # 允许缺失，但需监控
```

## Q3：订单状态枚举超出设计假设

### 发现

```sql
SELECT order_status, COUNT(*) FROM raw_orders GROUP BY 1 ORDER BY 2 DESC;
```

真实数据含 **8 种**状态，而模型最初只定义了 **5 种**：

| 状态 | 含义 | 是否在设计内 |
|---|---|---|
| `delivered` | 已送达 | ✅ |
| `shipped` | 已发货 | ✅ |
| `canceled` | 已取消 | ✅ |
| `invoiced` | 已开票 | ✅ |
| `processing` | 处理中 | ✅ |
| `created` | 已创建 | ❌ 新增 |
| `approved` | 已付款 | ❌ 新增 |
| `unavailable` | 不可用 | ❌ 新增 |

### 根因

枚举定义基于合成数据的简化假设，未接受真实数据校验。

### 影响

`created` / `approved` / `unavailable` 三种状态的订单流向未定义，
若不处理，新增状态会**静默混入**报表。

### 处理

扩充枚举定义至 8 种，并在数据字典中明确口径：

> **8 种状态中，仅 `delivered` 计入 GMV，其余 7 种均不计入。**

### 方法论沉淀

维度枚举值**不能靠想当然**，必须以真实数据分布为准。
这条质检规则的价值正在于此——它在**建模阶段**就暴露了
设计假设与现实的差距，而非等到报表出错后被业务方发现。

## Q4：GMV 口径不统一

### 发现

| 口径 | 金额（BRL） |
|---|---|
| 含全部订单 `gmv_all` | 15,843,553 |
| 仅已送达 `gmv_delivered` | **15,419,774** ← 标准口径 |
| **差异** | **423,779（2.67%）** |

### 说明

真实 Olist 中 96%+ 的订单为 `delivered` 状态，
因此口径差异为 **2.67%**（而非早期合成数据夸大的 58.2%）。

> ⚠️ **重要修正**：早期使用合成数据时曾得到 58.2% 的差异，
> 原因是合成数据的状态分布配置不合理（取消单占比过高）。
> **切换真实数据后修正为 2.67%。**
> 这正说明：指标口径结论必须建立在真实数据之上。

### 处理：口径下沉三步法

| 步骤 | 动作 | 落地位置 |
|---|---|---|
| ① 标记 | DWD 层统一生成 `is_delivered` 布尔标记 | `fct_orders.sql` |
| ② 约束 | 下游只准引用标记位，禁止自行过滤 status | 开发规范 |
| ③ 固化 | 数据字典写明"对外统一口径" | `schema.yml` |

同时在 ADS 层**保留三种口径字段**（`gmv_all` / `gmv_delivered` / `gmv_cancelled`），
让差异**显式可见**。

## Q5：review_id 主键失效（★ 质检规则否决设计假设）

> 详细修正说明见 `18_fix_record.md` 的 FIX-005

### 发现

```
dbt test → unique_stg_order_reviews_review_id  Got 789 results
          unique_fct_reviews_review_id        Got 789 results
```

### 现象与诊断

| 指标 | 数值 |
|---|---|
| 评价表总行数 | 99,224 |
| 唯一 review_id | 98,410 |
| **重复 review_id** | **789 个**（764 个对应 2 单、25 个对应 3 单） |
| **完全重复行**（id+order 都相同） | **0 条** |

**推演**：完全重复行 = 0 → 每个 `(review_id, order_id)` 组合唯一 → **组合键才是主键**。

验证：764×1 + 25×2 = 814 = 99,224 − 98,410 ✓

### 根因

**建模假设错误**——我以为 `review_id` 是主键（因为叫 "_id"），真实数据证明不是。

### 业务含义

reviews 与 orders 是**多对多**关系（业务设计本应一对一）：

| 方向 | 现象 |
|---|---|
| A：一单多评 | 一个 order_id → 多条 review_id |
| B：一评多单 | 一个 review_id → 多个 order_id ← 本次新增发现 |

### 处理

| 步骤 | 动作 |
|---|---|
| ① 自造代理键 | `review_key = review_id \|\| '-' \|\| order_id` |
| ② 质检规则迁移 | unique 从 `review_id` 移到 `review_key` |
| ③ 新增监控 | `is_shared_review_id` 标记，实测 1,603 行 |
| ④ 不在 ODS 去重 | 完全重复行=0，非脏数据，是真实业务关系 |

### 为什么不用"删掉质检规则"的省事做法

> 源系统没有可靠主键时，**数仓必须自己造一个**。
> 删质检规则等于把问题藏起来，下游仍会误用 review_id 当主键。

### 方法论沉淀

**这条质检规则的价值不在于"抓到脏数据"，而在于"否决了错误的设计假设"。**

如果没有这条 `unique`：
- 我会带着"review_id 是主键"的错误认知继续建模
- 下游所有按 review_id 的 JOIN / 去重逻辑都是错的

> **启示**：维度表/事实表的主键不能凭字段名想当然，
> 必须用 `SELECT COUNT(*) vs COUNT(DISTINCT)` 实测验证。
> 这是建模前的标准动作。
