> 📌 **术语说明**：本文档中的「质检规则」指对数据质量设定的自动校验条件，

## 导读：三个组件各管一段，互不重叠

这是理解整个技术栈最关键的一点——**它们不是三个"同类工具选一个"，而是三个职责层**：

```
┌──────────────────────────────────────────────────────────┐
│                    数据从哪来 → 到哪去                      │
└──────────────────────────────────────────────────────────┘

   源数据(CSV)          →    转换加工        →    展示
        │                       │                   │
        ▼                       ▼                   ▼
  ┌──────────┐          ┌──────────┐         ┌──────────┐
  │ DuckDB   │          │  dbt     │         │ Metabase │
  │          │  ◄─────► │  Core    │ ◄─────► │          │
  │ 存 + 算  │          │  转换    │         │  展示    │
  └──────────┘          └──────────┘         └──────────┘
   存储计算层              转换层               应用层
   "数据放哪、           "怎么加工、           "怎么给业务看"
    怎么算得快"          怎么管得住"
```

| 组件 | 职责 | 一句话 | 不做的事 |
|---|---|---|---|
| **DuckDB** | 存储 + 计算 | "数据放哪、怎么算得快" | 不管建模流程、不管展示 |
| **dbt Core** | 转换 + 治理 | "怎么加工、怎么管得住" | 不存数据、不搬运数据 |
| **Metabase** | 可视化 | "怎么给业务看" | 不加工数据、不替代数仓 |

**它们之间不存在"谁替代谁"**——就像砖刀、水平仪、抹子，各干各的活。

# 第一部分：DuckDB —— 存储与计算引擎

## 1.1 一句话理解

> **DuckDB 是"分析型的 SQLite"。**

| 数据库 | 解决的问题 | 部署方式 |
|---|---|---|
| **SQLite** | 单机场景，数据**怎么存**（事务型 OLTP） | 一个文件，无需装服务 |
| **DuckDB** | 单机场景，数据**怎么算得快**（分析型 OLAP） | 一个文件，无需装服务 |

SQLite 你可能听过——手机 App、浏览器、嵌入式设备里到处都是它，**不需要装数据库服务器**，就是一个 `.db` 文件。

DuckDB 把同样的"零部署"体验，带到了**分析查询**领域。

## 1.2 为什么它算得快：两个核心技术

### ① 列式存储（Columnar Storage）

**行存 vs 列存的直观理解**：

```
假设一张订单表有 3 列：订单号、金额、日期

【行存】（SQLite、MySQL、PostgreSQL）
┌─────────────────────────────┐
│ 001 │ 100 │ 2026-01-01 │  ← 第一行（所有字段挨着放）
│ 002 │ 200 │ 2026-01-02 │  ← 第二行
│ 003 │ 150 │ 2026-01-03 │
└─────────────────────────────┘
  读"金额"这一列 → 必须把每一行都整个读出来

【列存】（DuckDB）
订单号: [001, 002, 003]      ← 单独一摞
金额:   [100, 200, 150]      ← 单独一摞
日期:   [0101, 0102, 0103]   ← 单独一摞
  读"金额"这一列 → 只读那一摞，其他完全不碰
```

**为什么这对分析查询至关重要？**

分析查询的典型特征是：**扫描大量行，但只用其中几列**。

```sql
SELECT AVG(price) FROM order_items;   -- 10万行，但只要 1 列
```

- 行存：读 10 万行 × 全部字段（假设 8 列）→ 读 80 万个值
- 列存：只读 `price` 那一列 → 读 10 万个值

**I/O 直接少 87.5%** [citation:13]。再加上同列数据类型一致、重复值多，压缩率极高（低基数字段可压缩 90%+）[citation:1]。

### ② 向量化执行（Vectorized Execution）

**逐行 vs 向量化的直观理解**：

```
【逐行处理】（传统数据库）
  处理第1行 → 处理第2行 → 处理第3行 ...
  每行都要走一遍完整的函数调用流程

【向量化】（DuckDB）
  一次抓 1024~2048 行，打包成一个"批次"批量处理
  用 CPU 的 SIMD 指令（单指令多数据）并行计算
```

**类比**：
- 逐行 = 收银员一件一件扫码
- 向量化 = 整箱货物一起过 X 光机

**为什么快**（四个层次）[citation:7]：

| 层次 | 效果 |
|---|---|
| 减少函数调用 | 从 N 次降到 N/1024 次 |
| SIMD 并行 | 一条指令同时算 8/16/32 个数 |
| CPU 缓存友好 | 批次大小正好塞进 L1 缓存（32-128KB） |
| 分支预测友好 | 批量操作减少分支跳转 |

再加上**多核并行**（morsel-driven，把所有 CPU 核都用上）和 **zone maps**（记录每个数据块的 min/max，不相关的数据块直接跳过）。

### ③ 其他关键设计

| 设计 | 说明 |
|---|---|
| **C++ 从零编写，无外部依赖** | 完全掌控性能；跨平台行为一致 [citation:13] |
| **DataBlocks 存储布局** | 按列分块 + RLE/Dict/FSST 轻量压缩 + min/max 索引 [citation:4] |
| **混合 OLAP/OLTP** | 分析为主，同时不牺牲太多事务能力 [citation:4] |

## 1.3 与同类产品对比

| 维度 | DuckDB | SQLite | PostgreSQL / MySQL | Spark |
|---|---|---|---|---|
| **定位** | 嵌入式 OLAP | 嵌入式 OLTP | 服务端数据库 | 分布式计算 |
| **存储** | 列式 | 行式（B-tree） | 行式 | 内存/分布式 |
| **执行** | 向量化（1024-2048/批） | 逐行（VDBE） | 逐行 + 部分优化 | 分布式并行 |
| **并行** | 多核全开 | 单线程 | 多进程 | 集群 |
| **部署** | 一个文件，零配置 | 一个文件，零配置 | 需装服务、配权限 | 需搭集群 |
| **适合** | 本地分析、ETL、Parquet | App/嵌入式、小数据 | 业务系统、高并发写入 | TB-PB 级 |
| **扫描1亿行聚合** | ~2 秒 | ~60 秒 | 慢 | 快（但启动开销大） |

数据来源：[citation:10]

> **关键认知**：DuckDB 快不是因为它"更高级"，
> 而是因为它**只做分析这一件事**，并把这件事做到极致。
> SQLite 在"按主键查单行"上比 DuckDB 快——因为那是它的主场。

## 1.4 "嵌入式"意味着什么

**最大的实际好处：不需要装数据库服务。**

```
传统数据库（PostgreSQL/MySQL）
  下载 → 安装 → 配置端口 → 设用户名密码 → 启动服务 → 连接
  出问题还要看日志、重启服务

DuckDB
  pip install duckdb  →  直接用
  就是一个 .duckdb 文件，跟 Word 文档一样拷来拷去
```

**对你这个项目的意义**：
- 数据库文件可以直接删掉重建，**试错成本为零**
- 整个项目可以塞进 U 盘带走

## 1.5 在你机器上的实测表现

你的配置：AMD Ryzen 7 PRO 4750U（8 核）+ 32GB 内存

| 场景 | 表现 |
|---|---|
| 全量刷新 12 个模型 | **约 1.5 秒** |
| 74 项数据质检规则 | **约 1.9 秒** |
| 数据量 | 11 万行明细，数据库文件 < 100MB |

> 1.5 秒的全量刷新意味着什么？
> **你一天可以迭代几十次**，改一个模型立刻看到结果。
> 这才是"效率高"的真正来源——不是工具多先进，是反馈周期足够短。

## 1.6 什么时候不该选 DuckDB

| 场景 | 原因 | 该选什么 |
|---|---|---|
| 数据量 > 单机内存数倍 | 单机有上限 | Spark / 云数仓 |
| 多人并发写入 | DuckDB 是单写者模型 | PostgreSQL |
| 需要高可用、故障恢复 | 无集群、无副本 | 云数仓 |
| 高频小事务（下单、支付） | 它是分析型的 | MySQL/PostgreSQL |
| 需要精细的权限管控 | 无用户体系 | 企业级数仓 |

# 第二部分：dbt Core —— 转换与治理层

## 2.1 一句话理解

> **dbt 给 SQL 补上了软件工程。**

原生 SQL 缺什么？

| 软件工程的能力 | 原生 SQL | dbt |
|---|---|---|
| 版本控制 | ❌ | ✅（就是 Git，.sql 文件） |
| 依赖管理 | ❌（谁先跑谁后跑全靠人记） | ✅ `ref()` 自动解析 |
| 单元测试 | ❌ | ✅ `dbt test` |
| 文档 | ❌（写在 Wiki 里，永远过时） | ✅ `dbt docs` 自动生成 |
| 复用 | ❌（复制粘贴） | ✅ 宏 / CTE |
| 环境隔离 | ❌ | ✅ dev/prod 自动切 schema |

**dbt 不执行 SQL——它生成并编排 SQL**，然后把执行交给数据库（这里是 DuckDB）。

## 2.2 ELT 中的 "T"

现代数据 pipeline 有两种范式：

| 范式 | 流程 | 转换在哪做 |
|---|---|---|
| **ETL**（传统） | Extract → **Transform** → Load | 专门的转换服务器 |
| **ELT**（现代） | Extract → Load → **Transform** | **在数仓里用 SQL 做** |

本项目是标准 ELT：

```
1. Extract+Load（E+L）  ← scripts/03_load_raw.py 把 CSV 装进 DuckDB
2. Transform（T）        ← dbt 用 SQL 做全部转换
```

**dbt 只做 T**。它不负责抽取数据、不负责调度。

> 这是新手最常见的误解：以为 dbt 是"ETL 工具"。
> **它是转换工具，不是搬运工具。**

## 2.3 五种物化策略

物化 = "这个模型最终以什么形式存在数据库里"。

| 策略 | 数据库中是什么 | 每次运行 | 适用 | 本项目 |
|---|---|---|---|---|
| `view` | 视图（不存数据） | 秒建 | ODS 贴源层 | ✅ 4 个 |
| `table` | 实体表 | **全量重建** | DWD/DWS/ADS | ✅ 8 个 |
| `incremental` | 实体表 | **只加新数据** | 大事实表 | ✅ 1 个 |
| `ephemeral` | 不落库，内联成 CTE | — | 小中间模型 | — |
| `snapshot` | 历史版本表 | 追加版本 | SCD Type 2 | ✅ 1 个 |

来源：[citation:8]

**为什么 ODS 用 view？** 三个理由：

1. 不占存储
2. 永远与源数据一致——源系统修正后无需重跑
3. 贴源层的职责就是"原样搬运"，没必要实体化

## 2.4 三大核心能力

### ① `ref()` —— 依赖与血缘

```sql
SELECT * FROM {{ ref('stg_orders') }}
```

**为什么不直接写表名？**

| 直接写表名的问题 | `ref()` 的解决 |
|---|---|
| 环境一变（dev→prod）schema 就变，写死就跑不了 | 自动切换 |
| 不知道该先跑哪个模型 | **自动解析依赖顺序** |
| 血缘图要手工画，必然过时 | **自动生成 DAG** |

> **你看到的血缘图不是画出来的，是 `ref()` 推出来的。**
> 这保证了血缘图永远和代码一致——手工维护的文档做不到这一点。

### ② `dbt test` —— 数据质检规则

**测试的本质**：一段返回"不该存在的行"的 SQL。

```sql
-- unique 测试（简化示意）
SELECT order_id FROM stg_orders
GROUP BY order_id HAVING COUNT(*) > 1
-- 返回 0 行 = 通过；返回 N 行 = 有 N 个重复值
```

四类内置测试 [citation:2][citation:11]：

| 测试 | 检查 | 本项目 |
|---|---|---|
| `unique` | 值不重复 | 主键 |
| `not_null` | 不为空 | 关键字段 |
| `accepted_values` | 在枚举范围内 | `order_status`（8 种） |
| `relationships` | 外键存在 | `customer_id` → `dim_customers` |

**你项目里的 74 项质检规则**就是这么来的，全部通过。

### ③ `dbt docs` —— 元数据与血缘

```bash
dbt docs generate   # 生成文档站点
dbt docs serve      # 本地预览
```

自动产出：
- 所有模型的说明（来自 `schema.yml` 的 `description`）
- 所有字段的说明
- **交互式血缘 DAG**

## 2.5 增量模型与两个必知的坑

```sql
{% if is_incremental() %}
WHERE order_date > (SELECT MAX(order_date) FROM {{ this }})
{% endif %}
```

**实测效果**：全量 135,000 行 → 增量只处理 15,000 行，**效率提升约 9 倍**。

### 坑 1：幂等性（Idempotence）

官方明确警告：增量模型是有状态的，**最容易破坏幂等性** [citation:5]。

> 幂等 = 同样的输入，跑几次结果都一样。

`append` 策略下，如果源数据有更新，重复运行会产生重复行。**必须设 `unique_key`**。

### 坑 2：迟到数据

10 月的订单，11 月才进系统——按 `MAX(order_date)` 过滤会**永久漏掉**。

解法：加回溯窗口

```sql
WHERE order_date > (SELECT MAX(order_date) FROM {{ this }}) - INTERVAL 7 DAY
```

## 2.6 快照：SCD Type 2

用于保留历史变化：

```
1月：客户住「圣保罗」
2月：搬到「里约」
```

直接 UPDATE 覆盖 → 1 月的"圣保罗订单"全部消失。

快照的做法：

| customer_id | city | dbt_valid_from | dbt_valid_to |
|---|---|---|---|
| C001 | sao paulo | 01-01 | 02-01 | ← 旧版本封口 |
| C001 | rio | 02-01 | NULL | ← 当前有效 |

**运行方式（易错）**：

```bash
dbt snapshot    # ✅ 正确
dbt run         # ❌ 跑不到快照
```

## 2.7 dbt 不做什么（关键认知）

| 不做 | 由谁做 |
|---|---|
| ❌ 抽取数据（E） | Fivetran / Airbyte / 自己写脚本 |
| ❌ 加载数据（L） | 同上 |
| ❌ 定时调度 | Airflow / GitHub Actions / cron |
| ❌ 存储数据 | DuckDB / Snowflake / BigQuery |
| ❌ 可视化 | Metabase / Tableau |

**清晰的能力边界，是专业度的体现。**

## 2.8 ★ 治理视角：dbt 是你的差异化武器

**这是对你（DAMA 认证 + 治理岗）最重要的一节。**

普通人的 demo 只证明"会写 SQL"。但 dbt 的三件套，恰好对应 DAMA/DCMM 的三个核心能力域：

| dbt 功能 | 产出的东西 | 对应的治理能力域 |
|---|---|---|
| `dbt test` | 38 条数据质检规则 | **数据质量** |
| `dbt docs` | 字段级数据字典 | **元数据管理** |
| `ref()` | 血缘 DAG | **血缘分析 / 元数据** |
| `schema.yml` | 指标口径定义 | **数据标准** |

> **关键洞察**：
> 你不是在"额外做治理"——**是让工具替你产出治理证据**。
> 只要按规范写好 `schema.yml`，血缘图和数据字典就自动有了。

这就是为什么这个项目对你特别合适：**同一份工作，同时证明实施能力和治理体系能力。**

# 第三部分：Metabase —— 可视化层

## 3.1 一句话理解

> **让业务方不看 SQL。**

数仓做到 ADS 层，数据只是"能查"。**业务方不看 SQL，他们只看图。**

有了看板，它是"一个能用的数据产品"。

## 3.2 五个核心概念

| 概念 | 说明 | 类比 |
|---|---|---|
| **Question** | 一个查询 + 一张图 | 一道题目 |
| **Dashboard** | 多个 Question 的组合 | 一张试卷 |
| **Model** | 加工过的、带元数据的数据集 | 标准答案 |
| **Collection** | 文件夹，用于组织和授权 | 文件夹 |
| **Metric** | 集中定义的可复用指标 | 公式表 |

来源：[citation:9][citation:6]

**Metric 的治理价值**：集中定义"总营收"怎么算，
保证不同人算出来的是同一个数——**这正是你 GMV 口径治理的延伸**。

## 3.3 MBQL 语义层

Metabase 有个叫 **MBQL**（Metabase Query Language）的中间层 [citation:12]：

```
用户拖拽操作 → MBQL（中间表示） → 具体数据库的 SQL
```

这带来跨数据库的能力：嵌套查询、隐式 JOIN、字段类型自动识别（自动知道某列是时间戳还是类别，从而推荐合适的图表类型）。

## 3.4 Metabase 不替代什么

官方定位很明确 [citation:15]：

> Metabase 位于数据库/数仓之上，**不替代**你的业务数据库、数仓、ETL 平台或数据质量流程。

**这一条很重要**：别指望 BI 工具能弥补建模的烂摊子。
如果数仓模型混乱，BI 层再怎么调也快不了、也准不了。

## 3.5 你踩过的坑：Metabase 不支持 DuckDB

Metabase 支持 20+ 数据库，但**官方没有 DuckDB 驱动**。

我在 `07_metabase_guide` 里给了两条绕法：

| 方案 | 做法 |
|---|---|
| A（推荐） | 把 ADS 表导出 CSV，再导入 Metabase |
| B | 用 DuckDB 的 SQLite 兼容层导出 `.sqlite`，Metabase 连它 |


> "Metabase 原生不支持 DuckDB，我用导出中间层的方式解决。
> 生产环境我会让 BI 直连数仓并做权限管控；
> 本项目数据只有 11 万行、更新频率低，导出文件能省掉整套驱动配置成本。"

**还有降级方案**：matplotlib 画 3 张图只要 20 分钟。
**跑通的降级方案 > 卡死的完美方案。**

## 3.6 什么时候不该选 Metabase

| 场景 | 该选什么 |
|---|---|
| 需要复杂的自助多维分析 | Tableau / Superset |
| 需要像素级精美的财务报告 | FineReport / PowerBI |
| 需要强大的语义层/metrics-as-code | Looker / Cube |
| 大型企业、复杂权限与合规 | 商业 BI |

   ② DuckDB 落库（E + L）
   data/warehouse/olist.duckdb
   ├─ raw_customers     99,441
   ├─ raw_orders        99,441
   ├─ raw_order_items  112,650
   └─ raw_products      32,951
        │
        │  dbt run（T）

   ③ 四层模型
   main_staging   stg_*      （view）
        ↓
   main_core      fct_orders / dim_*  （table）
        ↓

        │

        │
        ▼

# 第五部分：为什么不是别的

## 5.1 核心逻辑：规模匹配

**这是最重要的选型原则。**

| 数据规模 | 合适的技术 |
|---|---|
| 几十万行（本项目 11 万） | **DuckDB + dbt**（单机秒级） |
| 几千万 ~ 几亿行 | 云数仓 + dbt（BigQuery / Snowflake） |
| TB ~ PB 级 | Spark / Hive + dbt |

本项目 11 万行、数据库 < 100MB。在这个规模上引入 Hadoop/Spark：

> **用高射炮打蚊子**——增加数倍运维成本，却不带来任何收益。

## 5.2 对比表

| 组件 | 本项目选型 | 常见替代 | 为什么不选 |
|---|---|---|---|
| 存储计算 | **DuckDB** | Hadoop/Spark | 集群运维成本远超收益 |
| | | PostgreSQL | 需要装服务；分析性能不如列存 |
| 转换 | **dbt Core** | 手写 SQL 脚本 | 无依赖管理、无测试、无文档 |
| | | Informatica/DataStage | 商业软件、重、不适合个人项目 |
| 可视化 | **Metabase** | Tableau | 收费、重 |
| | | Superset | 功能强但上手慢 |

## 5.3 方法论 vs 工程挑战


| 维度 | 本项目 | 生产环境 |
|---|---|---|
| 数据规模 | 11 万行 | TB 级以上 |
| 源系统 | 4 个结构良好的 CSV | 数十个业务系统 |
| 协作 | 个人 | 多方协同 |
| 调度 | 手动 | 自动化 + 监控告警 |

> **但方法论是相通的**：
> 分层设计、维度建模、数据质检规则、元数据管理——
> 这些核心逻辑不会因为数据量增长而改变。
> **规模带来的是工程挑战，不是方法论挑战。**

主动说出这些边界，比硬吹"我这能支撑企业级"可信得多。

## 6.3 高频追问与应对

| 追问 | 怎么答 |
|---|---|
| "为什么不用 Spark？" | 规模不匹配。11 万行 Spark 启动开销比计算还大。规模到 TB 我会迁移，但建模方法论不变 |
| "dbt 和 Airflow 什么关系？" | dbt 只做 T（转换），不管调度。生产环境会用 Airflow 或 GitHub Actions 调度 dbt |
| "DuckDB 能支撑生产吗？" | 单写者模型、无高可用，不适合生产多并发。生产会迁到云数仓，dbt 代码几乎不用改 |
| "你的血缘图是手工画的吗？" | 不是，`ref()` 自动解析的。这保证血缘永远和代码一致，手工文档做不到 |
| "增量模型怎么处理迟到数据？" | 加回溯窗口，比如往前 7 天。另外 append 策略必须设 unique_key 保证幂等 |
| "Metabase 怎么连 DuckDB？" | 官方不支持，我用导出中间层解决，并说明生产环境会直连 |
| "SCD 为什么重要？" | 客户搬家后，历史订单的属地会失真。用快照保留版本，才能回答"1 月时这客户住哪" |

## 6.4 ★ 主动暴露边界，反而加分


**主动说这三点**：

1. 数据量只有 11 万行，和生产的 TB 级不是一回事
2. DuckDB 是单机方案，生产要迁移
3. 调度是手动的，生产要用 Airflow

然后补一句：

> "但分层设计、维度建模、数据质检规则、元数据管理这套方法论是通用的，
> 规模增长带来的是工程挑战，不是方法论挑战。"

**这句话能直接把"项目小"的劣势，转成"方法论清晰"的优势。**

# 第七部分：常见误区

| 误区 | 正解 |
|---|---|
| "dbt 是 ETL 工具" | 它只做 T（转换），不管 E 和 L |
| "dbt 能调度" | 不能，调度靠 Airflow / cron / GitHub Actions |
| "DuckDB 是 SQLite 的替代品" | 不是，场景相反：SQLite 管事务，DuckDB 管分析 |
| "列存一定比行存好" | 不一定。按主键查单行，行存更快 |
| "BI 能弥补模型缺陷" | 不能。模型乱，BI 再调也快不了 |
| "增量模型一定更快" | 小表全量反而更简单可靠；增量有幂等和迟到数据的坑 |
| "血缘图要手工维护" | 用 `ref()` 就自动有了，手工维护必然过时 |
| "项目大才显得厉害" | 项目小但方法论清晰 + 能说清边界，比吹大的可信 |

## 附录 A：版本说明（易混淆）

你 `dbt debug` 输出里看到的：

```
dbt=1.12.0
duckdb=1.11.0     ← 这是【dbt-duckdb 适配器】的版本，不是 DuckDB 引擎
```

| 组件 | 版本 | 说明 |
|---|---|---|
| dbt Core | 1.12.0 | 转换框架本体 |
| dbt-duckdb | 1.11.0 | 让 dbt 能连 DuckDB 的适配器插件 |
| DuckDB 引擎 | 见 `requirements.txt` | 真正执行 SQL 的数据库 |

> **dbt 的适配器机制**：dbt Core 本身不认任何数据库，
> 靠 `dbt-duckdb` / `dbt-snowflake` / `dbt-bigquery` 这类适配器对接。
> **所以换数据库时，dbt 代码几乎不用改**——这也是 dbt 的核心价值之一。
