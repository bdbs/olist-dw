# 更新交付规范

> 版本：V1.0
> 制定日期：2026-09-11
> 适用范围：本项目后续所有更新、修正、补丁
> 约束对象：AI 助手（每次回复必须遵守）

---

## 核心原则

> **只给需要替换的文件，且每次必须交代清楚：
> 哪里改了、为什么改、改的逻辑是什么。**

---

## 一、三条硬性要求

### 要求 1：只交付变更文件

| 允许 | 禁止 |
|---|---|
| ✅ 本次真正修改过的文件 | ❌ 未改动的文件（凑数） |
| ✅ 新增的文件 | ❌ 整个项目压缩包（作为唯一交付） |
| ✅ 完整文件内容（可直接覆盖） | ❌ 只有片段、让用户自己拼 |

**文件内容必须是完整的**，不是 `...（中间省略）...`，
用户复制保存即可直接覆盖同名文件。

### 要求 2：必须说明「哪里修改了」

**必须有精确定位**，三选一（按可读性选）：

```
方式 A：diff 风格（推荐）
    models/staging/stg_order_reviews.sql  第 33-35 行
    - CAST(review_id AS VARCHAR) AS review_id,   -- 主键
    + CAST(review_id AS VARCHAR)||'-'||CAST(order_id AS VARCHAR) AS review_key,
    + CAST(review_id AS VARCHAR) AS review_id,   -- 非唯一

方式 B：行号定位
    models/marts/core/fct_reviews.sql
    第 55 行  新增：COUNT(*) OVER (PARTITION BY r.review_id) AS shared_id_count
    第 108 行 新增：CASE WHEN rv.shared_id_count > 1 ... AS is_shared_review_id

方式 C：表格对比
    | 位置 | 改动前 | 改动后 |
    |---|---|---|
    | schema.yml 第 42 行 | `unique` | 移除 |
```

**禁止**只说"已更新 `xxx.sql`"而不给出改了哪一行。

### 要求 3：必须说明「为什么修改」

三个层次，缺一不可：

| 层次 | 说明 | 示例 |
|---|---|---|
| **触发原因** | 什么现象导致这次修改 | "dbt test 报 unique 失败 789 条" |
| **根本原因** | 为什么会出这个现象 | "我误以为 review_id 是主键" |
| **业务/技术含义** | 这个问题意味着什么 | "reviews 与 orders 是多对多关系" |

## 二、修改逻辑的写法要求

### 2.1 必须给出备选方案对比

**每次做设计决策时，必须列出备选方案并说明为何不选**：

```markdown
| 方案 | 做法 | 为什么不选 |
|---|---|---|
| A | 删掉 unique 质检规则 | 把问题藏起来，下游仍会误用 |
| B | **改用组合代理键** | ✅ 选中：源系统无主键时数仓应自建 |
| C | 降级为 warn | 主键问题不该仅警告 |
```

**禁止**只给出最终方案，不说考虑过什么。

### 2.2 必须说明「为什么不做某件事」

反向论证往往比正向说明更有价值：

| 该回答的问题 |
|---|
| 为什么不在 ODS 层去重？ |
| 为什么不改 `is_latest_review` 的逻辑？ |
| 为什么不用 LEFT JOIN 而用 INNER JOIN？ |
| 为什么保留脏数据而不是过滤掉？ |

### 2.3 必须提供依据

| 类型 | 说明 |
|---|---|
| **实测数据** | 优先给真实数字（如"完全重复行 = 0"） |
| **规范条款** | 引用 `14_modeling_standards` 的具体条目 |
| **外部权威** | 引用 Kimball / DAMA / 官方文档 |

**禁止**凭"我觉得""一般是这样的"下结论。

## 四、禁止事项

| 禁止 | 说明 |
|---|---|
| ❌ 说"已修复"但不给文件 | **已犯 2 次**（FIX-005、FIX-006）：验证了方案却没写入文件 |
| ❌ 发布前不回读校验 | 必须 `grep` / 读取确认改动真的存在 |
| ❌ 只给方案不给成品 | "你可以这样改" ≠ 帮你改好 |
| ❌ 代码片段让用户自己拼 | 必须给完整可覆盖的文件 |
| ❌ 一次塞十几个未改动文件 | 只给变更文件 |
| ❌ 用"一般做法""通常"下结论 | 必须给依据 |
| ❌ **声称新增文件但未创建** | **见 FIX-006，必须自检文件是否真在磁盘上** |

> ⚠️ **最高优先级教训（FIX-006）**：
> 描述一个文件的功能、逻辑、参数说明，**不等于创建了这个文件**。
> 写回复前必须先确认文件已在磁盘上，再描述它。

## 五、★ 发布前质检流程（质检角色）

> **自 FIX-006 起强制执行**：每次交付前，AI 必须切换为「质检角色」独立复查。

### 5.1 为什么引入质检角色

| 项 | 内容 |
|---|---|
| **触发** | FIX-005、FIX-006 连续两次"声称已完成但文件未改动" |
| **根因** | 生成回复与写入文件是两个动作，缺少独立的交叉验证环节 |
| **含义** | 自己做的事自己检查，容易带着"我已经做了"的预设去看，会漏 |

**这与数据治理的理念一致**：

> 数据质量不能只靠"生产方自检"，必须有独立的质检环节。
> 交付件质量同理——**生成者 ≠ 质检者**。

### 5.2 质检流程（四道关）

```
┌─ 第 1 关：文件存在性 ────────────────────────┐
│  声明的每个文件，磁盘上是否真的存在？          │
│  → ls / Test-Path 逐个确认                    │
└──────────────────────────────────────────┘
                  ↓
┌─ 第 2 关：改动落盘 ──────────────────────────┐
│  声称改了的内容，文件里是否真有？              │
│  → grep 关键字 / 读取目标行确认                │
└──────────────────────────────────────────┘
                  ↓
┌─ 第 3 关：完整性 ────────────────────────────┐
│  文件是否完整可覆盖（无"省略"占位）？          │
│  YAML 能否解析？Python/PowerShell 语法是否通？ │
└──────────────────────────────────────────┘
                  ↓
┌─ 第 4 关：一致性 ────────────────────────────┐
│  文档数字与代码实际是否一致？                  │
│  新增文件是否被打包进交付包？                  │
└──────────────────────────────────────────┘
```

### 5.3 质检判定标准

| 关卡 | 检查项 | 不通过时 |
|---|---|---|
| 1 | 声明的新增文件存在 | 🔴 阻断，必须先创建 |
| 2 | 声称的改动 grep 得到 | 🔴 阻断，必须先写入 |
| 3 | YAML 可解析、语法无错 | 🔴 阻断 |
| 3 | 文件完整无省略 | 🔴 阻断 |
| 4 | 文档数字 = 代码实际 | 🟡 修正后放行 |
| 4 | 新文件已打包 | 🟡 补打包 |

### 5.4 质检输出格式

每次交付回复末尾必须附：

```markdown
【质检结果】

| 关卡 | 检查项 | 结果 |
|---|---|---|
| 1 文件存在性 | 声明 3 个新增文件 | ✅ 3/3 存在 |
| 2 改动落盘 | grep review_key × 2 处 | ✅ 匹配 |
| 3 完整性 | YAML 解析 / 语法校验 | ✅ 通过 |
| 4 一致性 | 文档数字 vs 代码 | ✅ 一致 |
| 4 打包 | 新文件在 zip 内 | ✅ 已包含 |

**质检结论**：通过 / 阻断（原因）

```

### 5.5 历史教训归档

| 编号 | 问题 | 教训 |
|---|---|---|
| FIX-005 | 声称修复 review 主键，4 个文件未改 | 验证 ≠ 落盘 |
| FIX-006 | 声称新增 apply_patch.ps1 + 规范章节，均未创建 | **描述 ≠ 创建** |

## 六、★ 补丁包交付标准（避免整包覆盖）

### 6.1 为什么改用补丁包

| 项 | 内容 |
|---|---|
| **触发** | 用户反馈："压缩包每次都要解压、复制粘贴覆盖所有文档" |
| **根因** | 此前一律交付完整包（88 个文件），其中可能只有 4 个真变了 |
| **含义** | 覆盖全部文件既慢，又有覆盖用户本地修改的风险 |

### 6.2 何时用补丁包 vs 完整包

| 场景 | 交付方式 |
|---|---|
| 变更 ≤ 10 个文件 | **补丁包**（默认） |
| 大版本重构、跨度过长 | 完整包 |
| 用户明确要求 | 完整包 |
| 首次获取项目 | 完整包 |

### 6.3 包内结构规定

```
补丁包内直接是项目相对路径，不含顶层目录：

patch.zip
├── models/
│   └── staging/
│       └── stg_order_reviews.sql
└── docs/
    └── 18_fix_record.md
```

> 若打包时带了 `olist-dw/` 前缀，`apply_patch.ps1` 会自动剥离。

### 6.4 应用补丁的两种方式

#### ⚠️ 中文路径警告（FIX-008，必读）

**PowerShell 5.1 的 `Expand-Archive` 解压含中文文件名的 ZIP 会报错**：

```
路径中具有非法字符
ConstructorInvokedThrowException
```

**根因**：Windows 中文环境默认 ANSI = GBK，
与 ZIP 内 UTF-8 文件名转换时产生非法字符。
（与早期 Python GBK 坑同源）

**三种解决方案**（按推荐度）：

| 方案 | 做法 | 适用 |
|---|---|---|
| **A（最稳）** | 资源管理器右键 → 全部提取 | 所有人，0 失败率 |
| **B（命令行）** | 用**英文包** + `Expand-Archive` | 命令行用户 |
| **C（命令行）** | Python 解压（见下） | 不想下载英文包时 |

```powershell
# 方案 C：Python 解压（绕开 Expand-Archive）
.venv\Scripts\python.exe -c "import zipfile;zipfile.ZipFile(r'D:\projects\olist-dw_patch_kpi.zip').extractall('.')"
```

> **打包约定（今后）**：
> 补丁包内部路径**优先使用 ASCII**，规避所有编码问题。
> 用户在中文版项目应用后可自行重命名。

#### 方式 A：直接解压（推荐，无需脚本）

补丁包内部结构**与项目目录一致**（`docs/`、`scripts/` 层级相同），
因此**直接解压到项目根目录即为覆盖**，无需任何脚本：

```powershell
cd D:\projects\olist-dw
Expand-Archive -Path "D:\projects\olist-dw_补丁包_FIX006.zip" -DestinationPath . -Force
```

或在资源管理器中：右键补丁包 → 全部提取 → 目标选 `D:\projects\olist-dw` → 覆盖。

#### 方式 B：用 apply_patch.ps1（有预览和清单）

```powershell
cd D:\projects\olist-dw
.\scripts\apply_patch.ps1 -PatchZip olist-dw_补丁包_FIX006.zip

# 预览模式（不实际覆盖）
.\scripts\apply_patch.ps1 -PatchZip olist-dw_补丁包_FIX006.zip -WhatIf
```

> ⚠️ **脚本只能用于第 2 次及以后的补丁**——
> 因为脚本本身就在补丁包里，首次使用时它还不存在（自举问题，见 FIX-007）。
> **首次必须用方式 A。**

#### ⚠️ 占位符必须替换为真实文件名

交付说明中的 `补丁包名.zip` 是**占位符**，必须替换为实际文件名，
例如 `olist-dw_补丁包_FIX006.zip`。每次交付必须给出**真实文件名**。

脚本行为：
1. 解压到临时目录
2. 自动探测并剥离顶层目录
3. 列出待覆盖文件清单
4. 执行覆盖
5. 清理临时目录

### 6.5 脚本设计决策

| 决策 | 备选 | 为什么不选 |
|---|---|---|
| **用 Copy-Item 逐文件覆盖** | `robocopy /MIR` | `/MIR` 会**删除目标中多余的文件**——用户自建文件会被误删，风险太高 |
| **UTF-8 BOM 编码** | 无 BOM UTF-8 | ⚠️ PowerShell 5.1 按 ANSI 读无 BOM 文件，中文注释乱码（与之前的 GBK 坑同源） |
| **自动探测顶层目录** | 强制规定结构 | 打包时可能带前缀，自动探测更容错 |
| **提供 -WhatIf** | 无预览 | 覆盖前能先看清单，降低误操作风险 |
| **校验 dbt_project.yml** | 无校验 | 防止用户在错误目录执行 |

### 6.6 必须附的清单

补丁包说明中必须包含：

| 内容 | 要求 |
|---|---|
| 变更文件表 | 每个文件的类型（新增/修改）与改动摘要 |
| 改动明细 | 每个文件改了哪一行，diff 或行号 |
| 修改原因 | 为什么改 + 备选方案对比 |
| 验证结果 | 实测数据 |
