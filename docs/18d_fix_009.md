## 一、为什么更新

### 1.1 触发

用户发现 3 个文档文件名乱码：

```
18b_FIX-006_璇存槑.md
19_鏇存柊浜や笉瑙勫勫.md
21_鍙戝鐕璐ㄥ...md
```

### 1.2 根本原因

**文件名以 UTF-8 编码存储，但解压工具按 GBK（中文 Windows 默认 ANSI）解码。**

技术链条：

```
正确名 "说明"  →  UTF-8 字节: E8 AF B4 E6 98 8E
                     ↓ 被当作 GBK 读
                E8AF → 璇
                B4E6 → 存   ← 字节错位，从这里开始全乱
                988E → 槑
                → 显示 "璇存槑"
```

**为什么字节会错位**：
UTF-8 中文是 **3 字节**，GBK 中文是 **2 字节**。
用 2 字节规则去切 3 字节序列，切点必然错位，且错一个全乱。

### 1.3 与之前问题的关系

| 编号 | 现象 | 共同根因 |
|---|---|---|
| 早期 | Python 读中文注释报 GBK 错 | **Windows 中文环境默认编码假设** |
| FIX-008 | `Expand-Archive` 报"非法字符" | 同上（文件名层） |
| **FIX-009** | **文件名乱码** | **同上（文件名层）** |

**三次踩同一个坑**，说明这不是偶然，是环境特性。

### 1.4 为什么内容没坏

**文件名编码 和 文件内容编码 是两回事。**

| 项 | 受影响 |
|---|---|
| 文件名 | ❌ 乱码 |
| 文件内容 | ✅ 完好（UTF-8 原样写入） |

已用 md5 验证：3 个文件内容与源文件**完全一致**。

**程序自己读文件名，不依赖人输入** —— 绕开了这个死结。

## 四、修改明细

### `scripts/fix_garbled_names.py`

| 行号 | 内容 |
|---|---|
| 20-35 | `KNOWN_NAMES` 已知正确名映射表（兜底用） |
| 40-56 | `try_recover()` —— **GBK 往返还原**核心算法 |
| 58-66 | `try_known()` —— 编号前缀匹配兜底 |
| 68-76 | `is_mojibake()` —— 乱码判定 |
| 78-130 | 主流程：扫描 → 判定 → 还原 → 重命名 |
| 88 | 支持 `--dry-run` 预览 |

### 核心算法（两行）

```python
recovered = name.encode("gbk").decode("utf-8")
```

**原理**：把误读过程**反过来走一遍**

```
乱码名 --gbk编码--> 原始UTF-8字节 --utf8解码--> 正确名
```

### 为什么还要 `KNOWN_NAMES` 兜底

部分文件名含 **GBK 无法表示的字节**（如 `0xA3`），
解压时该字节已被丢弃，**往返转换会失败**。

例如 `21_release_qc_checklist.md`：
```
"检" = E6 A3 80  →  0xA3 在 GBK 中非法  →  解压时被丢弃  →  无法还原
```

此时用**编号前缀**匹配已知正确名（`21` → `21_release_qc_checklist.md`）。

### 为什么脚本只扫 `docs` 和根目录，不递归

| 考虑 | 说明 |
|---|---|
| 安全 | 避免误动 `data/raw/` 里的 CSV（那些名字本来就该是英文） |
| 性能 | 项目文件集中在 docs |
| 可控 | 出问题影响范围小 |

## 五、为什么这样改（修改逻辑）

**决策 1：为什么脚本用 ASCII 命名**

| 方案 | 后果 |
|---|---|
| 命名为 `修复乱码.py` | ❌ 它自己也会乱码，讽刺且不可用 |
| **`fix_garbled_names.py`** | ✅ 全 ASCII，任何环境都能正确显示 |

**这是从三次踩坑中得到的直接教训**：
**跨工具传递的路径优先用 ASCII。**

**决策 2：为什么要 `--dry-run`**

重命名是**不可逆**操作（虽然可改回，但要重新识别）。
预览模式让用户先看会发生什么，符合"高危操作先预览"惯例。

**决策 3：为什么目标文件已存在时删除乱码副本**

场景：用户先解压了中文包（乱码），后来又解压了英文包（正确）。
此时两个文件都存在。

| 方案 | 评价 |
|---|---|
| 保留两个 | ❌ 文档重复，容易看错版本 |
| **删除乱码副本** | ✅ 内容一致（md5 已验证），保留正确的那个 |

**决策 4：为什么不顺带把项目改成英文文件名**

| 方案 | 评价 |
|---|---|
| 全项目改英文 | ❌ 用户明确选了中文版，且中文名对阅读友好 |
| **保持中文名 + 交付通道用 ASCII** | ✅ 兼顾可读性与兼容性 |

> **核心原则**：
> 中文名在"人看"时友好，在"工具处理"时脆弱。
> **项目命名用中文，交付通道用 ASCII** —— 两者可以兼得。
