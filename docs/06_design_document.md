# 电商主题域数据仓库建设方案

> 版本：V1.0
> 编制日期：2026 年 9 月
> 技术栈：DuckDB + dbt Core + Metabase（全本地、零现金成本）

---

> 📌 **术语说明**：本文档中的「质检规则」指对数据质量设定的自动校验条件，
> 业内标准术语叫「**断言**」（英文 assert，对应 dbt 的 `test` 功能）。
> 例如「订单ID不能重复」就是一条质检规则。

## 摘要

本方案以 Olist 巴西电商公开数据集为业务载体，设计并落地一套四层分层的数据仓库，完成从业务需求到数据治理落地的端到端实践。

项目覆盖 ODS 贴源层、DWD 明细层、DWS 汇总层、ADS 应用集市层共 **11 个数据模型**（另含 1 个增量模型），构建「1 个事实表 + 2 个维度表」的星型模型，处理订单明细 **112,650 行**。数据源为 Kaggle Olist 真实数据集，含 99,441 笔订单、覆盖 24 个月经营周期。

核心治理成果：

- **指标口径统一**：量化 GMV 口径差异（含取消订单口径较标准口径多 423,779 BRL，占比 **2.67%**），通过 DWD 层标记位下沉与数据字典固化，消除口径分歧
- **数据质量保障**：建立 5 类共 74 项数据质检规则，自动化校验通过率 100%
- **元数据管理**：输出字段级数据字典与端到端血缘 DAG，覆盖全链路 12 个模型

本方案同时可作为 DCMM 2.0 数据架构、数据标准、数据质量、元数据管理四个能力域的落地示例。

## 一、项目背景与业务需求

### 1.1 业务背景

Olist 是巴西的一家电商平台，连接中小商家与主流电商渠道。平台运营过程中积累了订单、客户、商品、卖家等核心业务数据，但数据分散在多个业务系统的原始表中，存在以下问题：

| 问题 | 具体表现 |
|---|---|
| 数据分散 | 订单信息在订单表，商品金额在明细表，客户属地在客户表，无法直接关联分析 |
| 口径不清 | 订单存在 5 种状态，不同部门对"成交额"的计算口径不一致 |
| 无法追溯 | 报表数字异常时，无法快速定位到是哪个环节、哪张表的问题 |
| 重复开发 | 各分析师重复编写相同的关联逻辑，效率低下且易出错 |

### 1.2 业务需求

业务方提出的核心诉求：

1. **GMV 趋势监控**：按月度观察成交总额变化，识别增长或下滑拐点
2. **品类结构分析**：哪些品类贡献主要收入，各品类占比如何
3. **客户价值分层**：识别高价值客户与流失风险客户，支撑精细化运营

### 1.3 需求拆解：从业务问题到数据问题

这是数据从业者的第一道能力门槛——**把业务语言翻译成数据语言**。

| 业务需求 | 数据问题 | 解决方案 |
|---|---|---|
| GMV 趋势 | GMV 的**定义**是什么？含不含取消订单？ | 定义标准口径并下沉到 DWD 层 |
| 品类结构 | 品类字段在哪张表？要不要关联？ | 建商品维度表，事实表外键关联 |
| 客户价值 | 用什么模型分层？R/F/M 怎么算？ | RFM 模型，窗口函数 NTILE 打分 |

**关键洞察**：业务方说"GMV"时，默认以为所有人都知道它是什么。但实际上，这个看似简单的指标，恰恰是本次项目中差异最大的风险点。

## 二、架构设计

### 2.1 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│                      数据源层（CSV 文件）                        │
│   customers / orders / order_items / products                 │
└───────────────────────────┬──────────────────────────────────┘
                            │  03_load_raw.py（装载）

└───────────────────────────┬──────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  DWD 明细层  models/marts/core/      物化：table               │

│  产出：dws_customer_rfm（客户价值主题）                         │
└───────────────────────────┬──────────────────────────────────┘
                            │  dbt ref()
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  ADS 应用集市层  models/marts/analytics/  物化：table           │
│  ─────────────────────────────────────────────────────────   │
│  职责：面向具体报表/看板，一表一应用                             │
│  产出：ads_gmv_monthly / ads_category_sales / ads_region_...   │
└───────────────────────────┬──────────────────────────────────┘
                            │
                            ▼
                    ┌───────────────┐
                    │  Metabase BI  │
                    └───────────────┘
```

### 2.2 分层设计的核心原则

**为什么要分层？** 一句话：**让每一层的职责单一，从而让问题可定位、变更可隔离、逻辑可复用。**

| 原则 | 说明 | 违反的后果 |
|---|---|---|
| **职责单一** | ODS 只搬运，DWD 只建模，ADS 只服务报表 | 逻辑混杂，一处改动处处报错 |
| **依赖单向** | 只能上游依赖下游（`ref()` 强制约束） | 循环依赖，无法调度 |
| **口径下沉** | 指标口径在 DWD 层定义一次，下游只引用 | 各写各的，报表对不上 |
| **可回溯** | ODS 保留原始数据，可重算 | 算错了无法还原 |

### 2.3 技术选型与理由

| 组件 | 选型 | 选它的理由 | 什么时候不该选 |
|---|---|---|---|
| 存储计算 | **DuckDB** | 列存向量化，分析查询性能优异；单文件免运维；本项目数据量 < 100MB | TB 级以上、多租户、需资源隔离 |
| 建模工具 | **dbt Core** | 把 SQL 建模变成软件工程：版本控制、测试、文档、依赖管理全部内置 | 需要图形化编排、复杂调度依赖 |
| 可视化 | **Metabase** | 开源免费，JAR 版免 Docker，10 分钟上手 | 需要复杂自助分析、企业级权限 |
| 版本管理 | **Git** | 变更可追溯、可回滚 | — |

**选型的本质判断**：本项目数据量 12 万行、数据库文件 < 100MB。在这个规模下引入 Hadoop/Spark，属于**用高射炮打蚊子**——增加了数倍的运维成本，却不带来任何收益。

架构决策的核心不是"追新技术"，而是**匹配场景**。同时也要清醒认识到方案边界：若数据量增长到 TB 级、需要多租户资源隔离，则应迁移至 Spark 或云原生数仓。

### 2.4 物化策略

| 层级 | 物化方式 | 理由 |
|---|---|---|
| ODS | `view`（视图） | 不占存储，永远与源数据一致；贴源层无需实体化 |
| DWD | `table`（实体表） | 星型模型被下游高频引用，实体化避免重复计算 |
| DWS/ADS | `table`（实体表） | 直接服务 BI 查询，要求响应快 |

## 三、数据模型设计

### 3.1 星型模型

```
                    ┌──────────────────┐
                    │  dim_customers   │
                    │──────────────────│
                    │ customer_id (PK) │
                    │ customer_state   │
                    │ region           │
                    │ is_core_market   │
                    └────────┬─────────┘
                             │ customer_id
                             │
    ┌──────────────────┐     │     ┌──────────────────┐
    │  dim_products    │     │     │   fct_orders     │
    │──────────────────│     │     │──────────────────│
    │ product_id (PK)  ├─────┴─────┤ order_item_key PK│
    │ product_category │ product_id│ customer_id  FK  │
    │ product_cat_cn   │           │ product_id   FK  │
    │ weight_tier      │           │ order_date       │
    └──────────────────┘           │ order_amount     │
                                   │ is_delivered     │
                                   │ is_cancelled     │
                                   └──────────────────┘
```

**事实表**：`fct_orders`，粒度为「一笔订单中的一个商品」，共 **112,650 行**，含 3 个度量值（price、freight_value、order_amount）。

> ⚠️ **重要说明**：源订单表有 99,441 笔订单，但事实表去重后仅 **98,666** 笔。
> 差额 **775 笔**为「无明细订单」——订单表存在但明细表无对应记录。
> 详见第 5.4 节「静默数据丢失」。

**维度表**：
- `dim_customers`（96,096 行）：客户属地维度
- `dim_products`（32,951 行）：商品品类维度

### 3.2 为什么用星型模型

| 对比维度 | 星型模型 | 雪花模型 | 三范式 |
|---|---|---|---|
| 表数量 | 少 | 较多 | 多 |
| 查询 JOIN 次数 | 少（1 跳） | 多 | 很多 |
| 查询性能 | **高** | 中 | 低 |
| 冗余 | 有 | 少 | 无 |
| 业务可读性 | **高** | 中 | 低 |
| 适用场景 | **分析型（数仓）** | 折中 | 事务型（业务库） |

数仓服务于分析查询，**查询性能和业务可读性优先于存储节省**。维度表的冗余（如 region 字段在每行客户重复存储）以极低的空间代价，换取了查询时减少一次 JOIN——这是划算的权衡。

### 3.3 维度表设计的治理价值：派生字段下沉

`dim_customers` 在原始字段基础上，额外派生了两个字段：

| 字段 | 派生规则 | 治理价值 |
|---|---|---|
| `region` | 按州归集为 5 个大区 | 地理口径在维度层统一定义，避免各分析师自行归类标准不一 |
| `is_core_market` | SP、RJ 为 TRUE | 业务口径（核心市场定义）固化在模型中，而非散落在各报表 SQL 里 |

`dim_products` 同理，派生了 `product_category_cn`（中文品类名）和 `weight_tier`（重量档位）。

**设计思想**：把"口径"固化在维度表里，下游只能引用、不能重新定义。这是数据标准域的核心落地手段。

## 四、命名规范

### 4.1 分层前缀

| 前缀 | 层级 | 全称 | 含义 |
|---|---|---|---|
| `stg_` | ODS | Staging | 贴源层 |
| `dim_` | DWD | Dimension | 维度表 |
| `fct_` | DWD | Fact | 事实表 |
| `dws_` | DWS | Data Warehouse Summary | 汇总层 |
| `ads_` | ADS | Application Data Store | 应用集市层 |

### 4.2 字段命名

```sql
-- ✅ 规范
customer_id            -- 小写 + 下划线（snake_case）
order_purchased_at     -- 时间戳用 _at 结尾
order_date             -- 日期用 _date 结尾
is_delivered           -- 布尔用 is_ 开头
gmv_delivered          -- 金额带口径后缀
cancel_rate_pct        -- 比率带 _pct 后缀

-- ❌ 禁止
CustomerID             -- 驼峰命名
客户ID                  -- 中文字段名
flag / amount1         -- 语义不明
```

### 4.3 口径命名规则（本项目重点）

**同一个指标的不同口径，必须在字段名上区分，不能仅依赖注释。**

```sql
gmv_all          -- 含取消订单（错误口径，仅供对比分析）
gmv_delivered    -- ✅ 标准口径（对外统一使用）
gmv_cancelled    -- 取消订单金额
```

这条规则本身就是治理动作：**让口径错误在命名阶段就无法隐藏**。如果一个人引用了 `gmv_all` 出报表，review 时一眼就能看出来。

## 五、指标口径定义（本方案核心）

### 5.1 问题发现：GMV 口径差异 2.67%

订单状态共 5 种：

| 状态 | 含义 | 是否计入 GMV |
|---|---|---|
| `delivered` | 已送达 | ✅ 是 |
| `shipped` | 已发货 | ❌ 否（未确认收货） |
| `canceled` | 已取消 | ❌ 否 |
| `processing` | 处理中 | ❌ 否 |
| `invoiced` | 已开票 | ❌ 否 |

实测口径差异：

| 口径 | 金额（BRL） | 说明 |
|---|---|---|
| `gmv_all`（含全部状态） | **15,843,553** | ❌ 错误口径 |
| `gmv_delivered`（仅已送达） | **15,419,774** | ✅ 标准口径 |
| `gmv_cancelled`（取消金额） | **5,765,933** | 用于分析业务损失 |
| **差异** | **423,779（2.67%）** | **报表会虚高** |

**这意味着**：如果财务按 `delivered` 算、运营按全部状态算，两个部门报出的 GMV 会相差 423,779 BRL。

> 📌 **口径说明**：真实 Olist 数据中 96% 以上的订单为 `delivered` 状态，
> 故口径差异为 2.67%（早期用合成数据时曾得到 58.4%，原因是状态分布配置不合理）。
> **这正说明：指标口径结论必须建立在真实数据之上。**

### 5.2 解决方案：口径下沉三步法

#### 第一步：DWD 层定义标记位

在 `fct_orders` 中固化布尔标记，下游**只能引用标记位，禁止自行用 `order_status` 过滤**：

```sql
CASE WHEN orders.order_status = 'delivered' THEN TRUE ELSE FALSE END AS is_delivered,
CASE WHEN orders.order_status = 'canceled'  THEN TRUE ELSE FALSE END AS is_cancelled
```

#### 第二步：ADS 层显式暴露多口径

`ads_gmv_monthly` 同时输出三种口径金额，让差异**可见**而非隐藏：

```sql
SUM(order_amount)                                        AS gmv_all,        -- ❌ 含取消
SUM(CASE WHEN is_delivered THEN order_amount ELSE 0 END) AS gmv_delivered,  -- ✅ 标准
SUM(CASE WHEN is_cancelled THEN order_amount ELSE 0 END) AS gmv_cancelled   -- 取消金额
```

**为什么不全砍掉 `gmv_all`？** 因为保留它有两个价值：
1. 让口径差异**可量化**，成为持续监控项
2. 业务如需分析"含取消的流水"，有现成字段可用，不必另写一套

#### 第三步：数据字典固化定义

在 `schema.yml` 中明确写入：

```yaml
- name: gmv_delivered
  description: ✅ 标准 GMV 口径（仅已送达订单）。对外报表统一使用此字段。
- name: gmv_all
  description: ⚠️ 含取消订单的金额，仅用于对比分析，不作为对外口径。
```

**治理思想**：口径问题不是"技术问题"，而是"管理问题"。技术手段（标记位、多口径字段、字典说明）的作用是**让分歧显性化**，而不是用权力强制统一。当差异摆在所有人都看得见的地方，共识自然容易达成。

### 5.3 ★ 静默数据丢失：775 笔无明细订单（核心治理案例）

#### 现象

```
源订单表 raw_orders        : 99,441 笔
事实表 fct_orders 去重后   : 98,666 笔
差额                      :    775 笔（0.78%）
```

**这 775 笔订单在订单表存在，但在订单明细表没有任何记录。**

#### 为什么这是最危险的问题

事实表的 JOIN 是**从明细表出发**的：

```sql
FROM stg_order_items items
INNER JOIN stg_orders orders ON items.order_id = orders.order_id
```

所有 112,650 行明细都能匹配到订单，**表面上一行不丢**。
但那 775 个"只有订单、没有商品"的订单，**永远不会进入事实表**。

| 对比项 | 口径差异（5.1 节） | 静默丢失（本节） |
|---|---|---|
| 性质 | **显性** | **隐性** |
| 表现 | 两个数字摆一起就看出来 | 不主动探查永远发现不了 |
| 报错 | 质检规则会失败 | **无任何报错、无日志、无告警** |
| 发现难度 | 低 | 高 |

> **数据工程中最危险的不是算错，是静默丢失。**
> 算错会有异常，丢失不会。

#### 处理方案：三层防御

**① 保持 INNER JOIN，不改 LEFT JOIN**

事实表粒度是"订单行"，本来就只应包含有明细的订单。
强行改成 LEFT JOIN 会让事实表出现 `product_id IS NULL` 的脏行，
污染所有下游聚合。**粒度纯洁性优先于统计完整性。**

**② ADS 层另建订单总数口径**

需要"订单总数"指标时，从 `stg_orders` 直接聚合，
而非从事实表反推：

| 指标 | 数据来源 | 数值 |
|---|---|---|
| 事实表订单数 | `COUNT(DISTINCT order_id) FROM fct_orders` | 98,666 |
| 订单表订单数 | `COUNT(*) FROM stg_orders` | **99,441** |

**③ 加 severity:warn 质检规则持续监控**

```yaml
- name: order_id
  tests:
    - relationships:
        to: ref('stg_order_items')
        field: order_id
        severity: warn     # 允许存在，但必须可见
```

> **`severity: warn` 的设计意图**：
> 这类问题业务上无法根治（确实存在无明细订单），
> 但必须**可见**。设为 warn 而非 error，
> 是"我知道它存在，并且我在监控它"的治理态度。

#### 方法论沉淀

| 原则 | 说明 |
|---|---|
| **丢失比错误更可怕** | 错误会报错，丢失不会 |
| **可见即可控** | 无法根治的问题，至少让它出现在监控里 |
| **粒度纯洁性** | 事实表粒度不能被"方便"破坏，宁可另建指标 |
| **先量化再决策** | 0.78% 可接受但必须知情；7.8% 则必须根治 |

### 5.4 核心指标定义表

| 指标名 | 业务定义 | 计算逻辑 | 数据口径 | 责任人 |
|---|---|---|---|---|
| GMV | 成交总额 | `SUM(order_amount) WHERE is_delivered` | DWD 层 `is_delivered` 标记 | 数据团队 + 财务 |
| 客单价 | 平均每单金额 | `gmv_delivered / 已送达订单数` | 分子分母**必须同口径** | 数据团队 |
| 取消率 | 取消订单占比 | `取消订单数 / 总订单数 × 100` | 全部状态订单 | 数据团队 + 运营 |
| 购买频次 | 客户下单次数 | `COUNT(DISTINCT order_id)` | 仅已送达 | 数据团队 |
| R 分 | 最近购买时间分 | `NTILE(4) OVER(ORDER BY last_order_date)` | 1=最久，4=最近 | 数据团队 |
| F 分 | 购买频次分 | `NTILE(4) OVER(ORDER BY frequency)` | 1=最低，4=最高 | 数据团队 |
| M 分 | 消费金额分 | `NTILE(4) OVER(ORDER BY monetary)` | 1=最低，4=最高 | 数据团队 |

> ⚠️ **新手最易犯的错**：客单价的分子排除了取消单，分母却用了总订单数。口径必须**分子分母同步**。

## 六、数据质量规则

### 6.1 质量设计思想

**质量是设计出来的，不是检查出来的。**

传统做法是先建表、后检查，问题往往在报表交付后才被发现。本项目采用**质检规则前置**：在建模阶段就把质量规则写成代码，每次 `dbt run` 后自动执行 `dbt test`，不通过则不允许发布。

### 6.2 质量规则清单

| 序号 | 规则类型 | 检查对象 | 规则内容 | 对应 DAMA 质量维度 |
|---|---|---|---|---|
| 1 | 唯一性 | `fct_orders.order_item_key` | 不可重复 | 唯一性 Uniqueness |
| 2 | 非空 | `fct_orders.order_amount` | 不可为空 | 完整性 Completeness |
| 3 | 值域 | `fct_orders.order_amount` | 介于 0 ~ 200,000 | 准确性 Accuracy |
| 4 | 非空 | `fct_orders.is_delivered` | 不可为空 | 完整性 |
| 5 | 参照完整性 | `fct_orders.customer_id` | 必须在 `dim_customers` 中存在 | 一致性 Consistency |
| 6 | 参照完整性 | `fct_orders.product_id` | 必须在 `dim_products` 中存在 | 一致性 |
| 7 | 枚举值 | `dws_customer_rfm.r_score` | 只能取 1/2/3/4 | 有效性 Validity |
| 8 | 唯一性 | `dws_customer_rfm.customer_id` | 不可重复 | 唯一性 |

**实测结果：74 项质检规则全部通过，通过率 100%。**

### 6.3 质量问题处理机制

当质检规则不通过时，按以下流程处理：

```
质检规则不通过
   ↓
定位根因（回溯 ODS 层原始数据）
   ↓
判断性质：采集丢失 / 录入错误 / 业务逻辑变更
   ↓
业务确认处理规则（丢弃 / 置空 / 归入异常表）
   ↓
修改模型逻辑
   ↓
补充质检规则防止复发
```

**关键**：每一步都要留下记录，形成《数据质量问题台账》。这份台账本身就是治理能力的证明。

### 6.4 已知的数据质量风险

| 风险 | 现状 | 后续处理 |
|---|---|---|
| INNER JOIN 丢弃无明细订单 | 本次数据中未出现（0 单） | 真实数据中可能出现，需监控丢弃行数 |
| 商品品类空值 | 本次未出现 | 维度表需处理，填入"未知" |
| 客户城市拼写不一致 | 已在 ODS 层用 `LOWER(TRIM())` 标准化 | 需持续监控 |

## 七、元数据与血缘管理

### 7.1 元数据覆盖范围

元数据是"关于数据的数据"。本项目通过 `schema.yml` 落地三层元数据：

| 元数据层级 | 内容 | 载体 |
|---|---|---|
| **模型级** | 模型用途、粒度、来源、注意事项 | `schema.yml` 的 `description` |
| **字段级** | 每个字段的含义、单位、口径 | `columns[].description` |
| **血缘级** | 模型间上下游依赖关系 | `ref()` 自动生成 |

### 7.2 血缘 DAG

dbt 根据 `ref()` 自动解析出全链路血缘：

```
stg_customers ──────────────► dim_customers ──┐
                                               │
stg_products ───────────────► dim_products ───┼──► ads_category_sales
                                               │
stg_orders ───┐                                │
              ├──► fct_orders ─────────────────┼──► ads_gmv_monthly
stg_order_items ─┘        │                    │
                          │                    └──► ads_region_overview
                          └──► dws_customer_rfm
```

**血缘的三大价值**：

1. **影响分析**：改 `fct_orders` 前，一眼看出会影响 4 张下游表
2. **根因追溯**：报表数字异常时，顺血缘向上逐级排查
3. **资产盘点**：哪些模型被高频引用（值得重点维护），哪些是孤岛（可下线）

### 7.3 数据字典

执行 `dbt docs generate` 后，dbt 自动把 `schema.yml` 中的描述渲染成**可在线浏览的数据字典网站**，包含：

- 全部 11 个模型的说明
- 每个模型的字段级描述
- 交互式血缘 DAG 图
- 每个字段的质量测试配置

这份文档即 DAMA 元数据管理知识领域的落地成果。

### 8.5 方案边界说明

本方案为**个人学习与实践项目**，与生产环境存在客观差距：

| 维度 | 本项目 | 生产环境 |
|---|---|---|
| 数据规模 | 12 万行 / < 100MB | 通常 TB 级以上 |
| 源系统 | 4 张结构良好的 CSV | 数十个业务系统 + 历史遗留 |
| 协作 | 个人完成 | 业务、开发、运维多方协同 |
| 调度 | 手动执行 | 自动化调度 + 监控告警 |

**但方法论是相通的**：分层设计、维度建模、数据质检规则、元数据管理这些核心逻辑，不会因为数据量增长而改变。规模带来的主要是**工程挑战**，而非方法论挑战。
