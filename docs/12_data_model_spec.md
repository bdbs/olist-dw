## 导读：三层模型是什么关系

数据建模分三步走，从抽象到具体：

```
┌─────────────────────────────────────────────────────────┐
│  概念模型（Conceptual Model）                             │
│  ─────────────────────────────────────────────────────  │
│  回答：业务里有哪些"事物"？它们之间什么关系？              │
│  受众：业务方、产品经理                                   │
│  工具：ER 图、业务术语表                                  │
│  产出：客户 - 下单 - 订单 - 包含 - 商品                    │
└───────────────────────────┬─────────────────────────────┘
                            │ 细化：加上属性、确定粒度
                            ▼
┌─────────────────────────────────────────────────────────┐
│  逻辑模型（Logical Model）                                │
│  ─────────────────────────────────────────────────────  │
│  回答：每个事物有哪些字段？主键外键是什么？                │
│  受众：数据建模师、开发                                   │
│  工具：星型模型图、字段清单                                │
│  产出：1 事实表 + 2 维度表，明确粒度与度量                 │
└───────────────────────────┬─────────────────────────────┘
                            │ 落地：考虑具体数据库特性
                            ▼
┌─────────────────────────────────────────────────────────┐
│  物理模型（Physical Model）                               │
│  ─────────────────────────────────────────────────────  │
│  回答：真实建什么表？什么类型？怎么存？                    │
│  受众：DBA、数据工程师                                    │
│  工具：DDL、dbt 模型                                      │
│  产出：main_core.fct_orders 等 12 张实际表                 │
└─────────────────────────────────────────────────────────┘
```

**一句话区分**：

| 层级 | 关注什么 | 类比 |
|---|---|---|
| 概念模型 | **有什么** | 建筑设计草图：几室几厅、动线怎么走 |
| 逻辑模型 | **怎么组织** | 施工图纸：每间多大、门开在哪 |
| 物理模型 | **怎么建** | 实际施工：用什么材料、怎么布线 |

# 第一部分：概念模型

## 1.1 业务过程识别

数据建模第一步不是画表，是**识别业务过程**——企业到底在"做什么事"。

Olist 电商平台的核心业务过程只有一个：

> **下单**：客户在某个时间，从某个卖家那里，购买了某些商品。

围绕这个过程，识别出 5 个业务实体：

| 实体 | 说明 | 在业务中的角色 |
|---|---|---|
| **客户 Customer** | 下单的人 | 行为的发起方 |
| **订单 Order** | 一次购买行为 | 业务过程本身 |
| **订单行 Order Item** | 订单中的一个商品 | 业务过程的明细 |
| **商品 Product** | 被购买的东西 | 行为的客体 |
| **卖家 Seller** | 售卖商品的人 | 行为的参与方 |

## 1.2 概念 ER 图

```
                    ┌──────────────┐
                    │    Customer  │
                    │    客户       │
                    └──────┬───────┘
                           │ 1
                           │
                           │ 下单 (places)
                           │
                           │ N
                    ┌──────▼───────┐
                    │    Order     │
                    │    订单       │
                    └──────┬───────┘
                           │ 1
                           │
                           │ 包含 (contains)
                           │
                           │ N
                    ┌──────▼───────┐
     ┌──────────┐   │  Order Item  │   ┌──────────┐
     │ Product  │───┤   订单行      ├───│  Seller  │
     │  商品     │ N │              │ N │  卖家     │
     └──────────┘   └──────────────┘   └──────────┘
        1                                  1
```

## 1.3 基数关系说明

| 关系 | 基数 | 含义 | 举例 |
|---|---|---|---|
| 客户 → 订单 | 1 : N | 一个客户可下多笔订单 | 张三下了 5 单 |
| 订单 → 订单行 | 1 : N | 一笔订单含多个商品 | 一单买了 3 件 |
| 商品 → 订单行 | 1 : N | 一个商品可被多次购买 | 手机卖了 100 次 |
| 卖家 → 订单行 | 1 : N | 一个卖家可卖多个商品 | 卖家 A 有 50 个商品 |

## 1.4 业务术语表（治理动作）

概念模型阶段最重要的治理产出是**统一业务术语**——避免同一个词不同人理解不同。

| 术语 | 定义 | 易混淆点 |
|---|---|---|
| **订单** | 一次完整的购买行为，有唯一订单号 | 不等于"商品件数" |
| **订单行** | 订单中的一个商品条目 | 一单 3 件商品 = 3 个订单行 |
| **GMV** | 已送达订单的成交总额 | **不含**取消、未发货订单 |
| **客单价** | GMV ÷ 已送达订单数 | 分子分母**必须同口径** |
| **客户** | 下单的人 | 同一自然人可能有多个 customer_id |

> 这份术语表本身就是 DCMM「数据标准」能力域的落地成果。

# 第二部分：逻辑模型

## 2.1 建模方法选择：维度建模

业界两种主流建模方法：

| 方法 | 提出者 | 核心思想 | 适用 |
|---|---|---|---|
| **维度建模** | Kimball | 以分析需求为导向，星型/雪花模型 | ✅ **数仓分析层** |
| 三范式建模 | Inmon | 消除冗余，企业级统一模型 | 业务系统 OLTP |

**本项目选维度建模**，因为数仓的核心目的是**支撑分析查询**，
而维度建模在查询性能和业务可读性上有压倒性优势。

## 2.2 粒度声明（最关键的一步）

> **粒度 = 事实表的一行代表什么。**
> 这是维度建模中最重要的决策，决定了能回答哪些问题。

| 候选粒度 | 能回答 | 不能回答 | 选择 |
|---|---|---|---|
| 一笔订单 | 总金额、订单数 | 单品销量、品类结构 | ❌ |
| **一笔订单中的一个商品** | 以上全部 | — | ✅ **选定** |
| 一个客户 | 客户汇总 | 时间趋势、品类 | ❌ |

**为什么选最细粒度？**

```
粒度越细，能回答的问题越多。

订单行粒度：
  可以上卷到订单（去重统计）
  可以下钻到商品（品类分析）
  ✓ 保留了最大分析灵活性

订单粒度：
  商品维度的分析能力【永久丢失】
  想补回来只能重做模型
```

> **维度建模第一原则：尽可能保留最细粒度。**

```

                        │     dim_customers      │
                        │────────────────────────│
                        │ customer_id     (PK)   │
                        │ customer_state         │
                        │ customer_city          │
                        │ region          [派生]  │
                        │ is_core_market  [派生]  │
                        └───────────┬────────────┘
                                    │ customer_id
                                    │
   ┌────────────────────────┐       │       ┌────────────────────────┐
   │     dim_products       │       │       │      fct_orders        │
   │────────────────────────│       │       │────────────────────────│
   │ product_id      (PK)   │◄──────┴──────►│ order_item_key  (PK)   │
   │ product_category       │ product_id    │ customer_id     (FK)   │
   │ product_category_cn[派]│               │ product_id      (FK)   │
   │ weight_tier     [派生] │               │ seller_id              │
   └────────────────────────┘               │ order_date             │
                                            │ order_month            │
        【维度表：描述"谁、什么、哪里"】        │ price                  │
                                            │ freight_value          │
                                            │ order_amount           │
                                            │ is_delivered    [口径] │
                                            │ is_cancelled    [口径] │
                                            └────────────────────────┘
                                          【事实表：描述"发生了多少"】
```

## 2.4 事实表设计

### 字段分类

事实表的字段只有三类：

| 类型 | 作用 | 本项目字段 |
|---|---|---|
| **外键** | 指向维度表 | `customer_id`、`product_id`、`seller_id` |
| **度量值** | 可聚合的数字 | `price`、`freight_value`、`order_amount` |
| **退化维度** | 有业务含义但不用单独建维表的字段 | `order_id`、`order_status`、`order_date` |

### 度量值设计

| 度量 | 类型 | 可加性 | 说明 |
|---|---|---|---|
| `price` | 金额 | ✅ 可加 | 商品价格 |
| `freight_value` | 金额 | ✅ 可加 | 运费 |
| `order_amount` | 金额 | ✅ 可加 | price + freight_value |

> **可加性**：能否跨任意维度 SUM。
> 金额、数量可加；比率、单价**不可加**（不能把客单价相加）。

### 口径字段（本项目的治理重点）

| 字段 | 定义 | 为什么要有 |
|---|---|---|
| `is_delivered` | 订单状态 = delivered | GMV 口径统一 |
| `is_cancelled` | 订单状态 = canceled | 质量分析 |

**设计意图**：把"哪些订单算 GMV"这个业务判断，
**在 DWD 层一次性定义**，下游只能引用、不能重新定义。

## 2.5 维度表设计

### dim_customers

| 字段 | 类型 | 说明 | 派生？ |
|---|---|---|---|
| `customer_id` | 字符串 | 主键 | — |
| `customer_state` | 字符串 | 州（2 位缩写） | — |
| `customer_city` | 字符串 | 城市 | — |
| `region` | 字符串 | **按州归集的大区** | ✅ 派生 |
| `is_core_market` | 布尔 | **SP/RJ 为核心市场** | ✅ 派生 |

### dim_products

| 字段 | 类型 | 说明 | 派生？ |
|---|---|---|---|
| `product_id` | 字符串 | 主键 | — |
| `product_category` | 字符串 | 品类（英文） | — |
| `product_category_cn` | 字符串 | **品类中文名** | ✅ 派生 |
| `weight_tier` | 字符串 | **重量档位** | ✅ 派生 |

### 为什么派生字段要放在维度表

**这是本项目的核心治理设计，值得重点理解。**

```
❌ 错误做法：在 BI 报表里写 CASE WHEN
   → 每个报表都要写一遍
   → 甲写的分档标准和乙不一样
   → 报表对不上，互相扯皮

✅ 正确做法：派生字段下沉到维度表
   → 逻辑只写一次
   → 全公司复用同一份定义
   → 口径天然一致
```

> **"计算下沉、口径统一"** —— 这是数据标准域的核心落地手段。

## 2.6 为什么是星型不是雪花

| 维度 | 星型（本项目） | 雪花 |
|---|---|---|
| 维度表层级 | 1 层（扁平） | 多层（规范化） |
| 查询 JOIN 次数 | 少 | 多 |
| 查询性能 | **高** | 中 |
| 存储冗余 | 有 | 少 |
| 业务可读性 | **高** | 低 |

数仓服务于分析，**查询性能和可读性优先于存储节省**。
维度表冗余（如 `region` 在每行客户重复存储）以极低空间代价
换取减少一次 JOIN —— 这笔交易划算。

## 3.3 物化策略

| 物化方式 | 用途 | 本项目 |
|---|---|---|
| `view` | 不占存储，查询时才计算 | ODS 贴源层 |
| `table` | 真实建表，查询快 | DWD / DWS / ADS |
| `incremental` | 只处理增量数据 | `fct_orders_incremental` |
| `snapshot` | 保留历史版本（SCD2） | `snap_customers` |

**为什么 ODS 用 view？**

1. 不占存储
2. 永远与源数据一致——源系统修正数据后无需重跑
3. 贴源层不需要实体化

## 3.4 主键与索引设计

| 表 | 主键 | 类型 | 说明 |
|---|---|---|---|
| `fct_orders` | `order_item_key` | **代理键**（拼接生成） | `order_id + '-' + order_item_id` |
| `dim_customers` | `customer_id` | 自然键 | 源系统主键 |
| `dim_products` | `product_id` | 自然键 | 源系统主键 |

> **代理键 vs 自然键**：
> 事实表主键由多个字段拼接而成（因为单一字段无法唯一标识一行），
> 这种"人为构造"的键叫代理键。

# 第四部分：核心代码逐行讲解

## 4.1 fct_orders.sql（事实表）

### 代码结构

```sql
WITH items AS (
    SELECT * FROM {{ ref('stg_order_items') }}
),
orders AS (
    SELECT * FROM {{ ref('stg_orders') }}
),
joined AS (
    SELECT ...
    FROM items
    INNER JOIN orders ON items.order_id = orders.order_id
)
SELECT * FROM joined
```

### 逐段讲解

#### ① `{{ ref('stg_order_items') }}` —— dbt 的灵魂

```sql
SELECT * FROM {{ ref('stg_order_items') }}
```

| 概念 | 解释 |
|---|---|
| **这是什么** | dbt 提供的函数，意思是"引用另一个模型" |
| **为什么不直接写表名** | 直接写 `main_staging.stg_order_items` 会有三个问题 |
| **问题 1** | 环境切换时表名会变（dev/prod 不同 schema），写死就跑不了 |
| **问题 2** | 无法自动判断构建顺序 |
| **问题 3** | 无法生成血缘图 |

**`ref()` 带来的三大能力**：

```
1. 自动解析依赖 → dbt 知道要先建 stg_* 才能建 fct_orders
2. 自动生成血缘 → docs 里的 DAG 图就是这么来的（无需手工维护）
3. 环境隔离    → dev/prod 自动切换 schema
```

> 这就是为什么血缘图能自动生成——**它不是画出来的，是 `ref()` 推出来的。**

#### ② CTE（`WITH ... AS`）—— 让 SQL 可读

```sql
WITH items AS (...),
     orders AS (...),
     joined AS (...)
SELECT * FROM joined
```

**大白话**：CTE 就是"给一段查询结果起个临时名字"。

好比写文章先列提纲：
- 先准备素材 A（items）
- 再准备素材 B（orders）
- 最后把 A 和 B 组合（joined）

**好处**：把一个复杂查询拆成几个简单步骤，每步都能单独调试。

#### ③ INNER JOIN —— 数据关联的代价

```sql
FROM items
INNER JOIN orders ON items.order_id = orders.order_id
```

| JOIN 类型 | 行为 | 行数影响 |
|---|---|---|
| `INNER JOIN` | 只保留两边都能对上的 | 可能减少 |
| `LEFT JOIN` | 保留左表全部，右表对不上填 NULL | 至少等于左表 |

**本项目用 INNER JOIN 的代价**：

```
源订单数        99,441
事实表去重订单   98,666
静默丢失           775（0.78%）
```

这 775 个"只有订单、没有明细"的订单，
因为 JOIN 是从明细表出发的，**永远进不了事实表，且无任何报错**。

详见 `11_quality_issue_log.md` 的 Q1。

#### ④ 拼接主键

```sql
items.order_id || '-' || CAST(items.order_item_id AS VARCHAR)
                                        AS order_item_key
```

| 片段 | 解释 |
|---|---|
| `\|\|` | SQL 的字符串拼接符（类似 Excel 的 `&`） |
| `CAST(... AS VARCHAR)` | 数字转字符串，否则无法拼接 |
| 结果 | 如 `00010242-1`，全局唯一 |

**为什么需要复合主键？**
因为 `order_id` 在一笔多商品订单中会重复出现，
只有 `order_id + order_item_id` 才能唯一标识一行。

#### ⑤ COALESCE —— 防空值传染

```sql
COALESCE(items.price, 0) + COALESCE(items.freight_value, 0)
                                        AS order_amount
```

**问题场景**：

```
price = 100,  freight = NULL
100 + NULL = NULL      ← 空值会"传染"整个算式！
```

**COALESCE(a, b) 的作用**：a 为空就取 b。

所以 `COALESCE(price, 0)` = 价格为空时按 0 处理，避免整个金额变 NULL。

#### ⑥ 口径标记位（★ 本项目治理核心）

```sql
CASE WHEN orders.order_status = 'delivered' THEN TRUE ELSE FALSE END
                                        AS is_delivered
```

**这行代码在做什么**：把"这个订单算不算 GMV"这个业务判断，
固化成一个布尔字段。

**为什么这么重要**：

```
❌ 没有标记位时：
   分析师甲：WHERE order_status = 'delivered'
   分析师乙：WHERE order_status IN ('delivered','shipped')
   分析师丙：不过滤，直接 SUM
   → 三个人报三个 GMV 数字

✅ 有了标记位：
   所有人都写 WHERE is_delivered = TRUE
   → 口径天然统一
```

**实测数据**（真实 Olist）：

| 口径 | 金额（BRL） |
|---|---|
| 全部订单 | 15,843,553 |
| 仅已送达 | **15,419,774** |
| 差异 | 423,779（2.67%） |

## 4.2 dws_customer_rfm.sql（RFM 分层）

### RFM 模型是什么

| 维度 | 英文 | 含义 | 方向 |
|---|---|---|---|
| **R** | Recency | 最近一次购买距今 | 越近越好 |
| **F** | Frequency | 购买频次 | 越多越好 |
| **M** | Monetary | 累计消费金额 | 越多越好 |

### 核心代码：窗口函数 NTILE

```sql
NTILE(4) OVER (ORDER BY monetary) AS m_score
```

**大白话解释**：

```
把所有客户按消费金额从小到大排队
       ↓
平均切成 4 段（四分位）
       ↓
最穷的 25% 标 1 分
次穷的 25% 标 2 分
次富的 25% 标 3 分
最富的 25% 标 4 分
       ↓
每个客户都拿到自己的分数，行数不变
```

### 窗口函数 vs GROUP BY（新手最易混淆）

| 对比 | GROUP BY | 窗口函数 `OVER()` |
|---|---|---|
| 结果行数 | **变少**（多行压成一行） | **不变**（每行附加一列） |
| 类比 | 把 50 人算成 1 个平均分 | 给 50 人每人标注"你排第几档" |
| 用途 | 汇总统计 | 排名、分档、累计 |

```sql
-- GROUP BY：50 人 → 1 行
SELECT AVG(score) FROM students;

-- 窗口函数：50 人 → 50 行，多了 rank 列
SELECT name, score,
       NTILE(4) OVER (ORDER BY score) AS rank
FROM students;
```

### 分群逻辑

```sql
CASE
    WHEN r_score >= 3 AND f_score >= 3 AND m_score >= 3 THEN '高价值客户'
    WHEN r_score >= 3 AND m_score >= 3                  THEN '重要保持客户'
    WHEN r_score <= 2 AND m_score >= 3                  THEN '重要挽留客户'
    WHEN r_score >= 3 AND f_score <= 2                  THEN '新客/低价值'
    ELSE '一般客户'
END AS rfm_segment
```

**实测分布**（真实数据）：

| 分层 | 说明 | 运营策略 |
|---|---|---|
| 高价值客户 | R/F/M 三项都高 | 重点维护、VIP 权益 |
| 重要保持客户 | 近期有购、消费高 | 交叉销售 |
| **重要挽留客户** | 消费高但长期未购 | **优先召回** |
| 新客/低价值 | 近期首购、频次低 | 引导复购 |
| 一般客户 | 其他 | 常规运营 |

## 4.3 增量模型（进阶）

### 核心代码

```sql
{% if is_incremental() %}
WHERE order_date > (SELECT MAX(order_date) FROM {{ this }})
{% endif %}
```

### 逐字解释

| 片段 | 含义 |
|---|---|
| `is_incremental()` | dbt 问："我是第几次跑？" 首次=False，之后=True |
| `{{ this }}` | 指代"当前这个模型自己"（已存在的表） |
| `MAX(order_date)` | 表里现在最新的日期 |
| `WHERE order_date >` | 只要比它更新的数据 |

**效果**（实测）：

```
全量刷新：重算 135,000 行
增量刷新：只处理 15,000 行  → 效率提升约 9 倍
```

### 两个必知的坑

| 坑 | 场景 | 解法 |
|---|---|---|
| **迟到数据** | 10 月订单 11 月才进系统 | 加回溯窗口：`MAX(order_date) - INTERVAL 7 DAY` |
| **历史修改** | 源系统改了历史订单金额 | 改用 merge 策略，或定期全量重建 |

## 4.4 SCD Type 2 快照（进阶）

### 问题场景

```
1月：客户张三住「圣保罗」，下 10 单
2月：张三搬到「里约」
```

如果直接 UPDATE 覆盖：

```
统计 1 月"圣保罗的订单" → 张三那 10 单消失 ❌
```

### 解法：保留历史版本

| customer_id | city | valid_from | valid_to |
|---|---|---|---|
| C001 | sao paulo | 2026-01-01 | 2026-02-01 | ← 旧版本"封口" |
| C001 | rio | 2026-02-01 | NULL | ← 当前有效 |

`valid_to IS NULL` = 现在有效。

### 运行方式（易错）

```bash
dbt snapshot      # ✅ 正确
dbt run           # ❌ 跑不到快照
```

# 第五部分：模型演进与维护

## 5.1 变更管理

| 变更类型 | 影响范围 | 处理方式 |
|---|---|---|
| 新增维度字段 | 下游报表 | 加字段 + 补数据字典 |
| 修改度量口径 | 所有历史报表 | **必须评审**，建议新增字段而非改原字段 |
| 新增维度表 | 事实表外键 | 改事实表 + 补外键质检规则 |
| 修改粒度 | 全链路 | ⚠️ 等于重做模型 |

> **改口径的最佳实践**：新增字段（`gmv_delivered_v2`），
> 让新旧口径并存一段时间，而非直接覆盖。

## 5.2 血缘的价值

dbt 通过 `ref()` 自动生成血缘 DAG，带来三个能力：

| 能力 | 场景 |
|---|---|
| **影响分析** | 改 `fct_orders` 前，一眼看出影响 4 张下游表 |
| **根因追溯** | 报表数字异常，顺血缘向上逐级排查 |
| **资产盘点** | 哪些表被高频引用（重点维护），哪些是孤岛（可下线） |
