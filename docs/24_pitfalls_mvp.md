## 阶段一：环境搭建（4 个）

### 坑 1：winget 装不上

| 项 | 内容 |
|---|---|
| **现象** | `winget install` 报找不到包 / 无响应 |
| **根因** | 系统版本旧 / 商店组件缺失 / 企业策略禁用 |
| **解法** | 放弃 winget，直接去官网下载安装包 |
| **教训** | 包管理器不是必须的，**能装上才是目的** |

### 坑 2：pip 装包报 TLS/SSL 错误

| 项 | 内容 |
|---|---|
| **现象** | `pip install` 报 `SSL: CERTIFICATE_VERIFY_FAILED` 或连接超时 |
| **根因** | 网络中间设备（代理/防火墙）拦截，或公司网络策略 |
| **解法** | 换国内镜像源：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple` |
| **教训** | 先把源配好，再装包 |

### 坑 3：pip 安装被杀软拦截

| 项 | 内容 |
|---|---|
| **现象** | 装到一半报权限错误，或 `.whl` 被删除 |
| **根因** | 安全软件把 pip 的临时文件当威胁 |
| **解法** | 用**虚拟环境**（`.venv`），或对杀软加白名单 |
| **教训** | **永远用虚拟环境**——既隔离依赖，又减少杀软误判 |

### 坑 4：★ GBK 编码错误（中文 Windows 头号坑）

| 项 | 内容 |
|---|---|
| **现象** | `UnicodeDecodeError: 'gbk' codec can't decode byte 0xae` |
| **根因** | 文件是 UTF-8，但 Python 默认按**系统编码 GBK** 读 |
| **解法** | `setx PYTHONUTF8 1`（永久）或 `$env:PYTHONUTF8=1`（临时） |
| **教训** | 中文 Windows 上跑任何 Python 项目，**第一件事就是设这个** |

> ⚠️ **这个坑后来又变体出现 3 次**（文件名乱码、Expand-Archive 非法字符、PowerShell 脚本 BOM），
> 详见坑 15、坑 16、坑 17。

## 阶段二：模型开发（7 个）

### 坑 5：★ Jinja 里用了 SQL 注释

| 项 | 内容 |
|---|---|
| **现象** | `dbt run` 报 Jinja 语法错误，指向 `config()` 块 |
| **根因** | 我在 `{{ config(...) }}` 里写了 `-- 中文说明`，<br>但 `{{ }}` 内是 **Jinja 语法，不认 SQL 注释** |
| **解法** | 注释写在 `config()` 外面，或改用 `{# #}` |
| **教训** | **不同语法层用不同注释符**：SQL 用 `--`，Jinja 用 `{#`，别混 |

**错误写法 vs 正确写法**：

```jinja
{{ config(
    materialized='incremental',   -- ❌ Jinja 不认
) }}

-- materialized：增量物化      ✅ 注释放外面
{{ config(materialized='incremental') }}
```

### 坑 6：★ DuckDB 整数除法陷阱

| 项 | 内容 |
|---|---|
| **现象** | 质量断言失败，发现一条 `order_id = 40001`，超出最大值 40000 |
| **根因** | `/` 在 DuckDB 是**浮点除法**，`CAST` 到 INTEGER 会**四舍五入**而非截断<br>`(120000-1)/3 = 39999.666` → `CAST` → `40000` → `+1` → `40001` |
| **解法** | 改用 `//`（整数除法，截断） |
| **教训** | **SQL 方言差异**：整数除法在 DuckDB 是 `//`，不是 `/` |

### 坑 7：字段名错位（合成 vs 真实）

| 项 | 内容 |
|---|---|
| **现象** | 换了真实数据后模型全崩，报字段不存在 |
| **根因** | 合成数据用 `customer_zip_code`，真实 Olist 是 `customer_zip_code_prefix` |
| **解法** | 在装载脚本加**字段名自动对齐**逻辑，兼容两种命名 |
| **教训** | **先对齐字段契约再建模**，否则换数据源就全崩 |

### 坑 8：schema 前缀导致表找不到

| 项 | 内容 |
|---|---|
| **现象** | `SELECT * FROM ads_gmv_monthly` 报表不存在 |
| **根因** | dbt 按 `dbt_project.yml` 的 `+schema` 配置，实际表名是 `main_analytics.ads_gmv_monthly` |
| **解法** | 查询时带完整前缀 |
| **教训** | dbt 生成的表名 = **目标库 + 自定义 schema + 模型名** |

| 层 | 实际表名 |
|---|---|
| staging | `main_staging.stg_orders` |
| core | `main_core.fct_orders` |
| analytics | `main_analytics.ads_gmv_monthly` |

### 坑 9：dbt docs serve 端口占用

| 项 | 内容 |
|---|---|
| **现象** | `dbt docs serve` 报端口 10048 被占用 |
| **根因** | 上一次 serve 的窗口没关，8080 还占着 |
| **解法** | `--port 8081` 换端口，或 `netstat -ano` 找到进程 kill 掉 |
| **教训** | 长驻服务用完就关 |

### 坑 10：git 未初始化 / target 被提交

| 项 | 内容 |
|---|---|
| **现象** | ① `git add` 报 `not a git repository` ② `target/` 被提交进仓库 |
| **根因** | ① 忘了 `git init` ② 没建 `.gitignore` |
| **解法** | 先 `git init`，再建 `.gitignore` 排除 `target/`、`data/`、`.venv/` |
| **教训** | **建仓库第一件事是写 .gitignore**，否则几百个编译产物进版本库 |

### 坑 11：★ YAML 多行文本缩进

| 项 | 内容 |
|---|---|
| **现象** | `dbt test` 反复报 `YAML parsing error`，手动改了三轮都不对 |
| **根因** | `description: >` 是**折叠块语法**，对缩进极敏感：<br>① 后续行必须严格缩进 ② 不能有空行 ③ 不能出现 `: ` |
| **解法** | **改用单行字符串** `description: "..."` |
| **教训** | YAML 里**能单行就别多行**，多行是缩进地狱的入口 |

**三条铁律**：只用空格不用 Tab / 同级严格对齐 / 子级多 2 空格。

## 阶段三：真实数据接入（3 个）

### 坑 12：★ review_id 主键失效（789 条重复）

| 项 | 内容 |
|---|---|
| **现象** | `unique_stg_order_reviews_review_id` 失败，789 条 |
| **根因** | **我的设计假设错误**——以为 `review_id` 是主键，实测不是 |
| **关键证据** | 完全重复行 = 0 → 说明 `(review_id, order_id)` 组合才唯一 |
| **解法** | 自造组合代理键 `review_key = review_id \|\| '-' \|\| order_id` |
| **教训** | **主键不能凭字段名想当然**，必须 `COUNT(*) vs COUNT(DISTINCT)` 实测 |

> ⭐ **这是断言最有价值的一次**：
> 它在**建模阶段**否决了我的错误假设。
> 如果没写这条 unique，错误会一路带到生产。

### 坑 13：订单状态枚举超出假设

| 项 | 内容 |
|---|---|
| **现象** | `accepted_values` 失败，返回 3 条 |
| **根因** | 合成数据只模拟 5 种状态，真实数据有 **8 种** |
| **解法** | 扩充枚举定义至 8 种 |
| **教训** | 枚举约束要**以真实数据分布为准**，不能靠设计假设 |

```
delivered / shipped / canceled / unavailable
invoiced / processing / created / approved
```

### 坑 14：断言失败时的心态

| 项 | 内容 |
|---|---|
| **现象** | 切换真实数据后 test 出现失败 |
| **认知** | **失败是好事**——说明断言真的在工作 |
| **做法** | 走五步法：探查 → 定位 → 判断性质 → 修复 → 补规则防复发 |
| **教训** | 合成数据"全绿"不代表没问题，**真实数据才能验证设计** |

## 阶段四：多主题域（2 个）

### 坑 15：★ geolocation 邮编重复（100万 → 1.9万）

| 项 | 内容 |
|---|---|
| **现象** | 接入 100 万行地理数据后，担心 JOIN 导致数据膨胀 |
| **根因** | 同一邮编重复几十到几百次（不同测量点经纬度微差） |
| **解法** | 按邮编聚合取**平均经纬度**（区域质心），保留 `measurement_count` |
| **教训** | **接入新表前先探查粒度**，不要假设"主键唯一" |

| 处理方式 | 结果 |
|---|---|
| 不处理直接 JOIN | ❌ 一笔订单 × 500 条测量 = 销售额翻 500 倍 |
| 聚合后 JOIN | ✅ 100 万 → 1.9 万，正常 |

### 坑 16：★ fan-out 扇出（金额虚高 12.5%）

| 项 | 内容 |
|---|---|
| **现象** | 汇总时发现金额对不上 |
| **根因** | 一笔订单多条评价，`JOIN` 后行数膨胀，`SUM` 翻倍 |
| **实测** | 错误写法 3,803,285.63 vs 正确 3,381,281.72，**虚高 12.5%** |
| **解法** | 用 `ROW_NUMBER()` 标记最新评价，下游用 `is_latest_review` 过滤 |
| **自检动作** | **写任何汇总模型后，都跑一次总额对比** |

> ⚠️ **最危险的坑**：不报错、不告警，只是数字悄悄变大。

## 阶段五：交付协作（4 个）

### 坑 17：★ 中文文件名乱码（GBK 误读 UTF-8）

| 项 | 内容 |
|---|---|
| **现象** | 文档名变成 `18b_FIX-006_璇存槑.md` |
| **根因** | 文件名是 UTF-8，解压工具按 **GBK** 解码<br>UTF-8 中文 3 字节 vs GBK 中文 2 字节 → **切点错位，错一个全乱** |
| **解法** | 脚本还原：`name.encode('gbk').decode('utf-8')` |
| **教训** | 与坑 4 同源，**中文 Windows 编码问题的第 2 次变体** |

### 坑 18：Expand-Archive 报"非法字符"

| 项 | 内容 |
|---|---|
| **现象** | `Expand-Archive` 解压中文名 zip 报 `路径中具有非法字符` |
| **根因** | PowerShell 5.1 对 ZIP 内 UTF-8 标志位处理不一致 |
| **解法** | ① 资源管理器右键解压 ② 用**全 ASCII 路径包** ③ Python `zipfile` 解压 |
| **教训** | **第 3 次踩编码坑** → 固化规范：交付通道一律 ASCII |

### 坑 19：补丁脚本自举问题

| 项 | 内容 |
|---|---|
| **现象** | 执行 `.\scripts\apply_patch.ps1` 报"无法识别" |
| **根因** | 脚本**本身就在补丁包里**——用它解压包含自己的包，逻辑上不可能 |
| **解法** | 首次用 `Expand-Archive` 直接解压，之后才用得着脚本 |
| **教训** | 任何工具都要回答"**第一次怎么装**" |

### 坑 20：占位符未替换

| 项 | 内容 |
|---|---|
| **现象** | 用户执行了 `补丁包名.zip`（占位符） |
| **根因** | 我在可执行命令里留了占位符 |
| **解法** | 命令中必须写**真实文件名**，占位符只出现在说明文字 |
| **教训** | **可执行命令里不能有占位符** |

## 数据质量类坑（业务坑，非技术坑）

这些不是"报错"，是**真实数据里的问题**，靠断言发现：

| # | 问题 | 数量 | 危险点 |
|---|---|---|---|
| 1 | **无明细订单** | 775 单（0.78%） | INNER JOIN 会**静默丢失**，无任何报错 |
| 2 | 商品品类缺失 | 610 条 | 维度 JOIN 连带丢弃销售记录 |
| 3 | 一单多评 | — | fan-out 导致金额虚高 12.5% |
| 4 | 一评多单 | 789 个 ID | 多对多关系，主键不成立 |
| 5 | 订单状态 8 种 | 3 种超出假设 | 枚举约束失效 |

> ⭐ **头号危险：静默丢失**
> 算错不可怕——两个数字一对比就发现。
> **丢了才可怕——你根本不知道少了。**

## 五个通用教训（可迁移到任何项目）

| # | 教训 | 来源 |
|---|---|---|
| 1 | **中文 Windows 上先设 `PYTHONUTF8=1`**，并全程用 ASCII 路径交付 | 坑 4/17/18 |
| 2 | **主键必须实测验证**，不能凭字段名想当然 | 坑 12/15 |
| 3 | **接入新表先探查粒度**，再决定要不要聚合 | 坑 15/16 |
| 4 | **写汇总模型后跑总额对比**，确认无 fan-out | 坑 16 |
| 5 | **断言失败是好事**——它在替你否决错误假设 | 坑 12/13 |
